# 翻譯品質、提示詞與架構審查（2026-10-17）

> 基準：`f46353d`（本機 HEAD 與初步審查的參考版本相同，沒有後續修正）。依專案慣例，版權作品只寫類型，不寫書名與角色名。
> 分類：**缺陷**＝可重現的程式錯誤（已補先失敗、後通過的測試）；**風險**＝設計上可能出錯，還沒有實際案例；**假說**＝提示詞與品質的推測，需要真實模型 A/B 才能下結論。

## 一、提示詞與 Markdown 的作用範圍

| 檔案 | 會不會進入模型請求 | 修改後何時生效 |
|---|---|---|
| `prompts/<task>/v<N>.md` | 會，是正式提示詞（每個步驟載入最新的 `vN`） | `load_prompt` 有 `lru_cache`：**同一個行程不會重讀**。CLI 每次執行都是新行程，下一次執行就生效；`ncte gui` 要關掉重開。 |
| `docs/*.md`、`README.md` | 不會 | 只給開發與維護參考 |
| `AGENTS.md` | 不會進入小說翻譯；會影響之後接手的 Coding Agent | — |

已存的資料不會因為改提示詞而自動重做：
- 譯文的快取鍵只看提示詞**主版本**（`translate/v1`），檔案雜湊（`#sha8`）只記錄（ADR-019）。同一個 `v1.md` 改字，舊譯文仍算有效；`ncte translate --dry-run` 會列出用舊修訂翻譯的段落數，要套用請 `retranslate` 或 `translate --force`。
- 讀的階段（場景分析、記憶整理、覆核、關係、印象、體例、定名）的結果存在資料庫，不看提示詞版本，要重讀才會更新。本次改的 `memory_update` 只影響之後重讀或新書的場景。
- 本次只改 `v1.md` 內容，沒有升主版本：現有工作區的譯文與記憶**不會失效、不會被重翻**。

## 二、問題清單

### 第一優先：錯誤被誤認為已修好

**A. 校稿後的重譯沒有語義驗證【缺陷，已修】**
- 路徑：`translation/review.py::_retranslate_with_feedback`，由 `review_scope`（審稿）、`context_pipeline.proofread_pass`、`reader_pass` 呼叫。
- 原本行為：
  1. 重譯請求只有原文、修正建議與前後文，**沒有現行譯文**；`proofread.FIX_NOTE` 要求「只改那個錯、其他照舊」，模型其實看不到「其他」是什麼。
  2. 新譯文只要通過程式 QA（字數、標記、假名…），就標 `succeeded`、計入 `fixed`，並把該單元**所有**開著的 high／審稿問題（不限這次要修的）一律標 `resolved`。
  3. 讀者檢查（只看中文）提出、重譯後的文字沒有再對照原文。
- 重現：日文「彼女は来なかった。」、舊譯「她來了。」、問題「原文是否定」，模擬重譯仍是「她來了。」→ 舊版標 `resolved`、`fixed+1`（`tests/integration/test_fix_check.py`，在 `f46353d` 上失敗）。
- 影響：所有作品；校稿數字會高估修正率，使用者看不到仍錯的句子。
- 修法（成本：每次修正多一次小請求，約為該批重譯的 20–40%）：
  - 重譯請求帶 `current_translation`，提示詞改成「以目前的譯文為底，只改被指出且原文確實支持的錯」。
  - 新增 `fix_check` 步驟（`prompts/fix_check/v1.md`）：對每個修正給原文、修前、修後、問題，回答 `fixed`／`issue_invalid`／`still_wrong`／`undecided`，另報 `new_error`（修正引入的新錯）。
  - 只有 `fixed`、`issue_invalid` 會結案，而且只結案**這次送去修的那幾筆**（以 finding id 對應）；其他留 `open`，新譯文維持 `needs_review` 並記 `fix_<結果>`。有新錯（`regressed`）時新譯文標 `rejected_fix`，書裡仍用舊譯文。檢查失敗、被擋、沒回答 → `fix_unchecked`，不算修好。沒有重試迴圈，最多一次檢查。
  - 人工譯文不會被機器修正覆蓋（`kept_human`，問題留給人）。
  - `review.fix_check: false` 可關閉；關閉時修正照樣寫入，但記 `fix_unverified`，**永遠不算 fixed**。
  - `qa_findings.translation_id`（migration 22，只加欄位）：問題記在它針對的譯文版本上；審稿清除時只清到被審的那一版。
- 副作用：多一個請求類型（成本表多 `fix_check`）；`needs_review` 數量會比以前多，這是以前被隱藏的數字。

**B. 被擋或未審的單元被當成已完成【缺陷，已修】**
- 路徑：`review.py::review_scope`；`context_pipeline.proofread_pass`、`reader_pass`。
- 原本行為：分段送審時某段被內容過濾擋下，其他段成功，整批仍 `reviewed += len(items)`；被擋單元的 job 標 `succeeded`，而且因為審稿者「沒有提出問題」，它原本的 high 程式標記被 `_clear_confirmed` 清掉、譯文改成 `succeeded`。校稿與讀者檢查同樣把被擋段落算進 `checked`／`read`，job 標 `succeeded`。
- 重現：`test_a_refused_unit_is_not_reviewed_and_keeps_its_findings`、`test_proofreading_counts_only_what_it_checked_and_checks_its_fixes`（舊版失敗）。
- 修法：審稿統計改為 `actually_reviewed`／`blocked`／`failed`／`skipped`／`resolved`／`pending`；被擋單元 job 標 `blocked`、不清任何問題；沒有譯文的標 `skipped`。校稿與讀者檢查只把真的讀到的段落算進去，有段落被擋或失敗時 job 標 `partial`（不是 `succeeded`）。
- 另外發現：`ncte recheck` 只看程式規則，會把仍有未結語義問題（審稿問題、待驗證的修正）的譯文從 `needs_review` 改回 `succeeded`【缺陷，已修】。

### 第二優先：人物、記憶與證據

**C. 動作描寫被升級成明確說話者【缺陷，已修】**
- 路徑：`analysis/dialogue.py::SPEECH_VERBS` 含「笑っ」「微笑」「苦笑」；`detect_tags` 的 `narr_tag`（台詞後另起一段）與 `before_tag`（台詞前一段）因此把「太郎は笑った。」當成發話標記；`speaker.resolve` 遇到唯一的發話標記時，模型回「無法確定」也會被蓋成 `explicit`，再進入口吻範例庫（`speech_examples`）。
- 重現：「君は犯人だ」／「カイトは笑った。」＋模型 unknown → 舊版 `explicit`（`tests/unit/test_dialogue.py`）。
- 修法：笑、微笑、苦笑只在用引用助詞「と」直接接在台詞後（「〜」とカイトは笑った）時算發話標記；另起一段或在台詞之前只算 `action`（線索），由模型判斷、交給覆核。
- 未改（風險）：台詞後另起一段的真正發話動詞（「カイトは言った。」）仍是 explicit，模型回 unknown 也一樣；實務上這種寫法幾乎都是說話者本人，改成推測會讓口吻範例大量減少，先不動。
- 說話對象（`to`）一律是模型判斷，沒有分明確與推測【風險，未改】：翻譯提示已寫明是「讀全書時判斷」，目前只影響你／妳，先觀察。

**D. 確定程度與觀點在轉換中遺失【缺陷，已修】**
- 追蹤結果：

| 步驟 | 原本 | 現在 |
|---|---|---|
| memory_update → facts | 存 `fact_type`／`certainty`／`source_viewpoint`／原文證據／揭露位置 | 同 |
| facts → translate（`retrieval.select_facts`） | 帶 type／certainty／viewpoint／原文 | 同 |
| facts → relations、impressions | 只剩「述語 受詞」，**「米娜認為 A 是 B 的哥哥」變成「A 是 B 的哥哥」** | `qualified_fact`：「〔米娜認為〕…」「〔敘述者的說法〕…」「…（推測）」 |
| relations → translate 人物卡、naming、impressions | 只剩「哥哥」，推測的關係看起來像確定 | 推測的關係附 `certainty: inferred` 或「（推測）」 |
| utterances → house_style 台詞 | 推測歸屬的台詞沒有標記，可直接定成固定口癖 | 標 `guess: true`，提示詞要求不可只憑推測台詞定習慣 |
| utterances → impressions | 已標 `guess` | 同 |
| 適用時間 | relations 有 `since`／`until`；facts 有揭露位置 | 同（未改） |

- 測試：`tests/integration/test_certainty.py`。

**E. 故事進度可見性不一致【缺陷，已修】**
- 路徑：`memory/retrieval.memory_context` 的稱呼表用 `display_name_zh`（全書最終名字）而不是此處可見的名字；`context_pipeline.batch_context` 的敘述視角（`narration.focal`／`narrator`）同樣；`analysis/proofread` 的說話者標籤與人物卡也是。人物卡本身（`character_view`）有正確過濾，其他欄位從側門把真名帶回去。
- 重現：讀前段「戴兜帽的少女」、後段揭曉真名，翻譯前段時的請求在 `address_terms`／`narration` 中出現真名（`tests/integration/test_spoilers.py`，舊版失敗）。
- 修法：`visibility.visible_names(book, upto)` 為唯一來源；稱呼、敘述視角、校稿說話者（以場景結尾為準，與翻譯批次的粒度一致）、校稿人物卡（以段落開頭為準）都改用它。
- 區分「全書理解用的背景」與「當下可以說出口的內容」：讀完全書後的步驟（關係、印象、體例、定名）本來就看全書，它們的輸出再進入翻譯時，人物卡、關係、稱呼都經過可見性過濾。
- 未改（風險）：`impressions.voice`（口吻）是全書整理的，提示詞只禁止 `role` 寫後期身分，`voice` 理論上可能帶出後期資訊；讀者檢查與規則確認的人物清單用最終名字（只用來判斷性別，不要求譯文補名字）。

**F. 撤回事實時看不到舊事實【缺陷，已修】**
- 路徑：`prompts/memory_update` 要求 `retracts_fact_ids`，但 `build_memory_payload` 沒有提供任何舊事實或 id，模型只能猜（猜錯被程式丟棄，等於撤回機制從未作用）。
- 修法：payload 加 `known_facts`（此場景人物相關、此前可見、未撤回的最近 30 筆，含 id、type、certainty、viewpoint）；提示詞區分狀態改變（不撤回）、舊說法被推翻（撤回）、角色認知改變（只能由同一角色的新認知撤回）；程式擋下「用客觀事實撤回某角色的認知」，誤會曾經發生過。
- 測試：`tests/integration/test_retractions.py`。

### 第三優先：提示詞可能造成的文學失真

**G. 敘事人稱【不一致，已修提示詞】**：程式（`narration.first_person_slip`）已排除原文本身寫第一人稱的段落，翻譯提示卻要求第三人稱場景「內心話也不要加『我』」。改成：原文省略主語時不要補「我」；原文自己寫了第一人稱（內心獨白、引用、日記、信件、夢境、局部視角）就照原文。

**H. 性別與口吻【假說，已小幅修提示詞，待 A/B】**：體例提示原本要求「與角色性別不符的中文說法不要用……不為製造反差而接受性別不符」，會把原作刻意的反差（女性用粗獷自稱、偽裝、模仿）修掉。改成：原文中性的說法不要選帶錯誤性別色彩的中文；原文刻意的反差保留；不因性別規定角色怎麼說話。上一輪實測的「儂 → 老身」仍符合新規則（年齡反差保留、不用男性的「老夫」）。校稿的 voice 類不再以「與角色性別不符」為錯，並排除原文本身變了口吻的情況。

**I. 固定稱呼抹平情境【假說，已小幅修提示詞，待 A/B】**：定名對代名詞要求「固定譯法」，翻譯要求「沿用既有譯法」。改成「預設譯法＋適用情況」，場合、情緒、關係明顯不同時依本句原文調整；人名與暱稱照舊一致。

**J. 口吻的情境與時間【提案，未改】**：見第四節。

**思夢樂範例【缺陷，已修提示詞】**：`memory_update` 的 wordplay 範例把虛構姓氏「高木」對上另一家連鎖店的台灣名稱，文化知識錯誤，而且會鼓勵「姓氏像品牌就是梗」的推論。改成通用原則：原文看得出在玩梗才列；原文證據與文化解釋分開；不因同音同字推斷品牌梗；沒把握寫「待查證」、不自補外國品牌中文名；譯註只在譯文傳達不了且有把握時才給。`analysis/reader.py` 註解中的同一錯誤對應一併改掉。

## 三、作品可驗收條件（已實作）

`reports/acceptance.py`；`ncte export` 會印出一行，匯出報告 JSON 有 `acceptance`。逐項：應翻段落都有譯文、沒有 `needs_review`、沒有開著的嚴重問題（只算針對現行譯文的）、所有修正都經過來源對照並結案、審稿／校稿／讀者檢查沒有被擋或失敗的段落、context 模式下對照校稿與讀者檢查跑完整本（`succeeded`，不是 `partial`）、人工修改仍是會匯出的文字、EPUB 驗證通過。

匯出永遠可以做（未完成的段落保留日文）；「可驗收」只表示流程每一步都做完、沒有靜默失敗，**不代表譯文品質合格**。

## 四、提案（未實作，需要決定或付費驗證）

### 4.1 快取與依賴追蹤
目前能知道：哪些譯文用了舊提示詞修訂（dry-run）、哪些術語是人工確認的（快取鍵）。不知道：哪段譯文用了哪一版的人物卡、關係、視角、稱呼表。建議（中等成本、不改既有資料）：每筆譯文另存 `deps_json`——當時送出的人物 id、關係 id、稱呼 id、敘述設定與體例的雜湊；人物資料或譯名改變時，用它列出「可能受影響的段落」，分成「只需重新驗證」（關係、視角改了）與「需要重翻」（人工改了譯名）兩類，交給使用者決定。不建議自動重翻。

### 4.2 角色口吻的情境化（J）
現況：`impressions.voice` 一段三十字、`house_style.habits` 全書固定。建議先不加欄位，改成：`habits.note` 必須寫適用情況（本次已在提示詞加一句）；若 A/B 顯示偽裝、身分轉變的作品口吻錯誤明顯，再把 `voice` 改成「長期特徵＋（對誰／何時）例外」兩段，只在該場景出場時送出，控制 token。

### 4.3 成稿編修（literary editing）
目的：意思正確但讀起來不自然的句子。設計成**可選、預設關閉**、每場景最多一次：輸入原文、譯文、場景口吻資料；只允許改用詞、語序、節奏、冗詞；輸出必須逐段標出改了什麼；之後每段都經過 `fix_check` 類的來源對照（沒有明確改善或有新錯就保留原譯）。
A/B 驗證：同一批 3 本 × 各 60 段，A＝現行、B＝加編修；由**不同於翻譯模型的評審**與至少一位人工盲評，看（1）忠實度錯誤數不增加（以挑戰集與人工標註）；（2）自然度偏好；（3）刻意的含糊、重複、口癖是否被抹掉（專項抽查）。估價：以現行 flash 等級模型，每 60 段的編修＋驗證約 US$0.02–0.05，全實驗含評審約 US$1–3；人工盲評約 2–3 小時。驗收：忠實度錯誤不增加、自然度顯著偏好 B，否則不上。

### 4.4 語義評測（第七節要求）
見 `docs/evaluation.md`「語義挑戰集」。重點：保留現有字詞級評測作回歸測試；新增帶上下文的挑戰集，每題有「錯譯會長什麼樣」的對照與人工判定準則，不用同一個模型生成、修改又評分。

## 五、值得付費 A/B 的項目（依優先序）

5. 成稿編修（4.3）。

## 六、目前能不能主張「高品質可讀譯本」
不能。已有證據：流程完整性（測試、EPUB 驗證）、兩次抽樣驗收中人工看過的問題、現有字詞級評測。缺少：（1）任何以人工標註、不同模型評審的語義正確率數字；（2）整章、整本的中文自然度評估；（3）校稿修復率與引入新錯的比例（本次才開始記錄 `fix_*` 結果）；（4）未審、被擋段落比例在真實作品上的數字（本次才開始正確計算）。本次修正讓這些數字**可以被量到**，但還沒量。
