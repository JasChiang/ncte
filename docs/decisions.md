# 架構決策紀錄（ADR）

每條決策：背景 → 決定 → 後果。遇到歧義時一律優先「保留原文／保護 EPUB／可追溯／低成本」。

## ADR-001 同步 httpx + daemon worker threads，而非 asyncio
- 背景：規格建議 async；但 SQLite 寫入、Ctrl+C 與「中斷時不可等待 120 秒逾時」三者在 asyncio 下較難保證。
- 決定：`httpx.Client`（同步、執行緒安全）＋每批一個 daemon thread（上限 `max_concurrency`），所有 DB 寫入共用一把 `RLock`；主執行緒只做排程、預算與中斷處理。
- 後果：Ctrl+C 立即返回並保存 checkpoint；尚在進行中的請求標記為「帳單未知」，其估計費用計入已花費。

## ADR-002 placeholder 語法 `⟦n⟧…⟦/n⟧`／`⟦n/⟧`
- 背景：模型不可接觸或產生 HTML。
- 決定：使用罕見的 Unicode 括號與數字編號；重建時只依「原始元素對照表」建立元素，模型文字只當作文字節點插入。驗證要求：每個標記恰好一次、成對標記正確巢狀、且父元素與原文相同（允許同層重新排序以符合中文語序）。
- 後果：模型無法注入任何標記；placeholder 錯誤的單元重試，最後保留原文。

## ADR-003 ruby 平坦化為 `漢字《かな》`
- 背景：日文讀音 ruby 不能套到中文詞上；但「強敵《とも》」之類的義訓帶有意義。
- 決定：抽取時把簡單 ruby（含 rb/rp、mono ruby）轉成 `base《reading》` 給模型參考；中文輸出為純文字（不輸出 ruby）。含巢狀元素或 `rtc` 的複雜 ruby → 整段保留原文並列入報告。QA 會偵測 `《かな》` 外洩。
- 後果：譯文不再有 ruby 標記（這是刻意的）；義訓由 prompt 指示以「強敵（朋友）」等方式保留。

## ADR-004 mixed block 以 inline run 為單位
- 背景：EPUB 目錄常見 `<li><a>章名</a><ol>…</ol></li>`，若整個視為不可翻譯，目錄就無法翻譯。
- 決定：同時含 block 子元素與文字的元素，依 block 子元素切成多個 inline run，各自成為單元（xpath 加 `#runK`）；重建時只替換該 run 的文字與行內元素。

## ADR-005 預算以 run 為單位、保守計算
- 決定：`--budget-usd` 是單次 run（含其 resume）的上限。已花費＝API 回報費用＋token 推估費用＋「帳單未知」請求的事前估計。估計採 1 token≈1 個 CJK 字、輸出×2 安全係數。
- 後果：可能提前停止（偏保守）；併發時最多超出「同時進行中批次」的估計誤差，報告中會顯示上限。

## ADR-006 快取鍵只納入「與單元相關的術語」
- 背景：規格要求術語版本變更要重新評估，但修改一個人名不應讓整本重翻。
- 決定：`glossary_version` 存的是「出現在該單元原文中的術語」的 hash。修改譯名 → 只有包含該詞的單元失效；`context_hash` 只記錄、不作為跳過條件。

## ADR-007 模型不存在即停止；fallback 必須明列
- 決定：每次 run 開始呼叫 `/models` 驗證；不存在 → `stopped_fatal`。只有 `openrouter.fallback_models` 有設定才切換，切換會寫入 run notes 與每筆譯文的 `model_id`。

## ADR-008 OpenRouter `:batch` 變體與 Batch API 不在 MVP
- `/models` 顯示 `google/gemini-3.8-flash:batch` 半價，但規格 §3.4 要求先確認依賴關係與快照；baseline 的批次彼此獨立，未來可加，context 模式因逐場景記憶不適用。目前未實作。

## ADR-009 API 403 視為致命錯誤
- 依規格 §3.3，401/402/403 立即停止。注意 OpenRouter 的 403 也可能是內容審查（guardrail）；這會停止整個 run，使用者可檢查後以 `resume` 繼續。

## ADR-010 OPF 識別碼不變
- 匯出只改 `dc:language` 與（若翻譯）`dc:title`；`dc:identifier` 保持原值以免破壞內部參照。部分閱讀器可能把譯本與原書視為同一本書（已知限制）。

## ADR-011 explicit 說話者只來自程式可驗證的發話標記
- 背景：規格要求「只有明確證據才能升格成 explicit」，且 inferred 不得汙染口癖庫。
- 決定：LLM 對說話者的任何主張最多是 `inferred`；`explicit` 只來自「と＋名字＋說話動詞」等規則、explicit 引號的續段、或人工。
- 後果：explicit 數量偏少但精確（評測 explicit precision 1.0）；口癖庫不會因模型誤判而自我汙染。

## ADR-012 角色名／別名必須逐字出現
- 新角色 `name_ja` 必須逐字出現在證據單元；別名必須在場景中獨立出現（不只是較長名字的子字串）。防止模型以外部知識或後文提前加入人名（劇透）。
- 不自動合併同一人的不同稱呼（例如「フードの少女」與「リリア」）；身分揭露以 fact 記錄並受可見性控制。

## ADR-013 可見性 horizon = 場景開始
- 翻譯某場景時只提供該場景開始前揭露的事實、摘要、物件狀態、例句；本場景的分析結果（含同場景後文）可用於內部判斷（`lookahead_scope=current_scene`），但 prompt 要求不得把推測寫成確定。
- 前後文（`context_after`）在所有模式都不跨場景（M6 評測時發現 baseline 原本會跨場景，已修正）。

## ADR-014 複查只對標記單元、最多一輪
- 依規格 §5.7：程式 QA 的 high 發現、說話者證據衝突、譯者 `possible_source_error` 才送複查；複查只給證據與建議，需重譯的單元帶意見重譯一次再跑程式 QA。避免潤稿整章與成本失控。

## ADR-015 評測使用全新 workspace
- 每個實驗／重複都在新的 workspace 執行，確保 A/B/C/D 不共用快取與記憶；代價是重複匯入（很便宜）。

## ADR-016 ruby 內的純文字行內包裝（如 Kobo `kobospan`）視為讀音底字
- 背景：Kobo 格式的書在每個 ruby 底字外包 `<span class="kobospan" id="kobo.x.y">`；原本一律視為複雜 ruby 而保留日文，實書測試中有 251 段（約 8%）因此無法翻譯。
- 決定：ruby 中「沒有子元素、非 void 的行內元素」的文字當作底字；ruby 本來就會被平坦化，這些包裝及其 id 隨之移除（只影響 Kobo 的閱讀位置定位）。巢狀包裝或 `rt` 內含標記仍視為複雜 ruby。若有連結指向被移除的 id，匯出驗證會報告斷裂錨點。

## ADR-017 內容審查拒絕不是致命錯誤（修訂 ADR-009）
- 背景：實書翻譯到第 54／83 場景時，Gemini 以 `PROHIBITED_CONTENT`（HTTP 403, `content_policy_violation`）拒絕一批內容平常的日常段落，整個 run 依 ADR-009 停止；同一段文字的場景分析卻通過，屬於誤判。
- 決定：403/400/200-body 中帶有內容審查標記（content_policy / PROHIBITED_CONTENT / SAFETY / blocked …）的錯誤歸為 `ContentBlockedError`：不重送同一批，對半切開以隔離被拒段落；最終被拒的單元保留原文並以 `content_blocked`（high）列入報告。其他 401/402/403/404 仍立即停止。400 錯誤保留供應商回傳的 metadata 以便診斷。被拒請求記為不計費（`cost_status=none`）。
- 後續選項（未實作）：允許使用者明確指定只用於被拒段落的 fallback 模型，並記錄譯文來源。

## ADR-018 自動譯名候選不使快取失效；審稿確認可清除程式標記
- 背景（實書）：記憶更新在全書過程中陸續新增譯名候選（含「男→CIA男子」「母」「姫」等普通名詞），使 185 段早已正確的譯文被判為過期；審稿模型已確認無誤的段落仍停在「待複查」。
- 決定：(1) 快取鍵的術語部分只計入人工確認（verified）的譯名；自動候選不觸發重翻（migration 4 以新定義重算既有譯文的 glossary_version）。(2) 自動譯名候選必須 ≥2 字且不是身分／親屬／群體等普通名詞（`lexicon.py`）；這些仍可登記為角色供說話者判斷。`ncte glossary prune` 清除既有的這類項目。(3) 程式 QA 標為 high 的段落經審稿模型檢視後若沒有 medium/high 問題，譯文改回 `succeeded`，發現狀態記為 `cleared_by_review`（仍保留在報告中）。審稿模型只能「清除程式的疑慮」，不能把推測升級為事實。

## ADR-019 實體與稱呼（entity / name forms）；prompt 小改版不使快取失效
- 背景（實書）：團體的正式名稱與通稱（「〇〇。通称黒鬼」）、角色的本名／愛稱／全名在譯名表是互不相關的條目，造成愛稱被壓成本名、正式名稱與通稱互換、雙關由來遺失（黒鬼→黑鬼，中文歧視用語）。
- 決定：譯名表每一列是一個「稱呼」，以 `entity_id` 歸屬實體，`form_type`（official/full/short/nickname/alias/title）與 `form_note`（雙關、由來）。連結需要證據：程式偵測「通称／愛称／略称／あだ名…」句型（pattern）、記憶整理模型提出（兩個稱呼都須在本場景逐字出現、證據句逐字存在，否則只是候選）、人工 `ncte names link`。每個連結記錄揭露位置，翻譯請求只看得到已揭露的稱呼與連結。翻譯時把同實體的其他稱呼（`same_entity_as`）一起給模型，並要求「原文用哪個稱呼就用哪個譯名」。新 QA：`name_form_substitution`（用了同實體另一稱呼的譯名）、`offensive_term`（中文歧視用語）。
- 快取：prompt 檔同一版本內的修訂（hash 變動）不再讓既有譯文失效，只有版本號變動（v1→v2）才會；dry-run 會列出用舊修訂翻譯的段落數，由使用者決定是否重翻。理由：小幅改善指示不應讓整本書（約 US$4）被迫重付。
- 後續：實體卡是人物關係圖、名詞索引與系列書繼承的基礎（未實作）。

## ADR-020 系列：一個系列一個資料夾與資料庫；故事位置 =（集數, 段落序號）
- 背景：使用者可能從系列的中間或最新一集開始翻，之後再補翻前面的集數；角色、譯名、劇情記憶要跨集共用，但不能把後面集數的內容洩漏給前面的集數。
- 決定：
  - `workspace/library.db` 是書庫索引（系列、每本書是第幾集）；`workspace/series/<名稱>/ncte.db` 保存一個系列所有集數的資料，原書副本放在同一資料夾。單本書是只有一集的系列。舊的單一 `ncte.db` 在第一次執行時自動拆分搬移（保留 `ncte.legacy-*.db`）。
  - 段落序號（ordinal）是匯入時依 EPUB spine 閱讀順序替每個翻譯單元編的流水號；故事位置是 `(volume_index, ordinal)`，可用 2.5 表示外傳，`ncte series set-volume` 可調整閱讀順序（位置以 join 即時計算，不必改寫資料）。
  - 知識（角色、譯名／稱呼、實體連結、事實、摘要、物件、口癖例句）以系列為範圍；所有防劇透比較改用故事位置：第 2 集看得到第 1 集，第 1 集（即使較晚才翻）看不到第 2 集之後揭露的事實、稱呼連結、角色與例句。
  - 例外：出現在本段原文中的詞，其譯名一律提供（為了跨集一致）——名字本身已在原文出現，不構成劇透；但同實體的其他稱呼與連結仍依揭露位置過濾。
  - 同一名字在系列中只有一個角色；在較早的集數中被看到時，首次出現位置往前移。

## ADR-021 實體卡是「誰是誰」的唯一依據
- 背景（實書）：實體卡已把某角色的全名連到本名，但角色表仍有兩個角色（場景分析在全名首次出現時另建了角色），導致台詞歸屬、口癖例句、事實被拆開；人物關係圖只是在顯示時湊合。
- 決定：兩個稱呼一旦連成同一實體（pattern、模型或人工），對應角色立即合併到正式名稱的角色：台詞歸屬、說話者假說、口癖例句、事實、實體參照全部轉移，被合併的名字成為別名，保留最早的首次出現位置（`merge_characters`、`reconcile_characters`）。場景分析遇到實體卡上已知的稱呼時直接對應既有角色。`ncte names sync` 可對既有資料執行一次。

## ADR-022 稱呼表、共用稱呼、系列翻譯風格
- 背景（實書，兩集系列）：日文的稱呼取決於「誰對誰說」，同一個人被不同角色用不同稱呼與敬稱叫（「S」「S 的暱稱」「姉ちゃん」），稱呼改變常是關係變化的訊號；實體卡只知道「這個稱呼屬於誰」，所以譯法無法依說話者保持一致。另有姊妹共用的小名「S 的小名」，一個稱呼只能屬於一個實體，自動連結把兩人併成一張卡。敬稱與角色語氣的處理方式則寫死在通用 prompt。
- 決定：
  - **稱呼表** `address_terms`：（說話者, 對象, 稱呼原文含敬稱）一列，記錄譯法與來源（譯名表 < 模型 < 人工；人工不被覆蓋）、首次與最近使用的故事位置、使用次數、說話者是否只是推測。說話者＝對象表示用名字自稱。來源：(1) 程式從說話者已判定（explicit/inferred，不含 unknown）的台詞找出角色的各種稱呼，最長比對並接上敬稱；每句台詞只計一次（`address_observations`），場景重新分析或人工改說話者時先撤回再重算。(2) 記憶整理模型回報稱呼與本場景譯文用的譯法（須逐字證據、角色 id 已知）。(3) `ncte names address-set`。翻譯請求附上「這批原文出現的稱呼」與「這批說話者的慣用稱呼」，只含本場景之前已出現的（防劇透），依首次使用排序。審稿也會拿到。
  - **共用稱呼** `form_senses`：一個稱呼保留原本的實體，另外記錄「也可能指誰」。自動連結若會把兩個各有多個稱呼的實體合併，改為記錄共用稱呼並列為待人工確認的合併候選；人工可 `names link --shared`，也仍可直接合併。翻譯請求在揭露之後附 `may_refer_to`，要求依上下文判斷、不確定時不補人名；稱呼表不會把共用稱呼歸給任何人。
  - **系列翻譯風格** `series.style_json`：敬稱處理（natural/explicit/omit）、自訂規則、角色語氣說明。預設風格不加入請求（既有快取與請求不變）；設定後每一批都附上規則與「本批出現或在場角色」的語氣說明。風格不納入快取鍵：它是對新譯文的指示，改了之後由使用者決定重翻哪些段落。
- 不做：稱呼表不自動判斷「誤用」或產生 QA 錯誤（稱呼改變本身可能是劇情）；交給翻譯與審稿模型參考。

## ADR-023 先讀再翻：整集讀完、定名，再開始翻譯
- 背景（實書對照繁中正式版）：context 模式原本逐場景「分析 → 翻譯 → 記憶整理」，名字與稱呼的譯法在第一次翻到時就由模型當場決定，之後沿用；當下模型還不知道人物關係（例如S媽媽叫「Aちゃん」，正式版依說話者分譯「A同學」，S調侃時才譯「A妹妹」）。人工譯者則是讀完全書才定名。
- 決定：
  - `context.read_first`（預設開）：第一輪依閱讀順序對本次範圍的每個場景做場景分析與記憶整理（此時沒有譯文，記憶只來自原文；譯名、稱呼譯法都是提案）；第二輪「定名」；第三輪依序翻譯並審稿。關掉時維持原本的逐場景交錯流程。
  - **定名** `naming`：把本集出現的角色名、名詞、稱呼（誰叫誰）連同出現次數與代表原句交給模型，要求每項給建議譯法、其他選項與理由（一次呼叫，不讀全文）。程式套用建議譯法（不覆蓋人工確認的譯名與人工稱呼譯法；來源排序：譯名表 < 模型 < 定名 < 人工），並把「有其他選項且重要」的項目（名詞出現 ≥5 次、稱呼使用 ≥3 次，或中文只剩一個字的人名）列為待確認，存在 `naming_proposals`。
  - `context.naming`：`review`（預設）有待確認項目時停在定名之後（run 狀態 `awaiting_names`），用 `ncte names proposals` 查看、`ncte names decide` 選擇或全部採用，再 `ncte resume` 繼續；`auto` 直接採用建議不暫停；`off` 不做定名。已定案（人工決定）的項目在系列後續集數不會再提案，只處理新出現的名字與稱呼。
  - 防劇透不變：記憶雖然在翻譯前就涵蓋整集，翻譯請求仍只附「本場景之前揭露」的資訊。定名提案本身可能引用後文（例如身分揭露），只給使用者看，不放進翻譯請求。
  - 已翻好的書不受影響；新流程用在新書與重翻。`ncte names propose` 可對已分析過的書單獨產生提案。
- 代價：呼叫次數相同（多一次定名）；第一段譯文要等整集讀完（約占總費用四成）才出現，若預算在第一輪用完，會沒有任何譯文。

## ADR-024 書籍資訊（封面、目次、注意事項、後記、版權頁）照常翻譯，但不做故事分析
- 背景（實書）：前言、目次、注意事項、後記、版權頁也被當成場景分析，作者、插畫家、發行者被建成角色（插畫家「のん」甚至被定名提案譯成人名），摘要出現「本場景為目錄」。
- 決定：依閱讀順序把每個內容檔分成 front／story／back（`epub/matter.py`）：故事從 EPUB 目錄中第一個「不是封面、目次等」的項目開始，之前都是 front；沒有可用目錄時看檔名與第一行。之後遇到後記、版權頁（目錄名稱、檔名或第一行）起到書末都是 back。`context.skip_book_matter`（預設開）：只含書籍資訊的場景不做場景分析與記憶整理（仍照常翻譯）；定名只計算故事本文中的出現次數。
- 定名待確認項目保存原文例句（分散取自全書，最多 3 句，`naming_proposals.context_json`），`ncte names proposals` 會列出，不送進模型請求。角色名稱本身是稱呼（「Aさん」）且與另一個角色重疊時，提案清單會提醒（台詞可能被歸錯）。

## ADR-025 譯註（以括號附在段落後）；台詞要口語
- 背景（對照繁中正式版）：主角的姓和日本一家服飾連鎖店同名的梗，正式版以括號譯註說明；我們的規則禁止在譯文加入原文沒有的說明，雙關因此遺失。另在兩本書看到台詞用了書面語直譯（「具壓倒性優勢呢」）。
- 決定：
  - 翻譯輸出多一個 `translator_note`（預設空字串），存在 `translations.translator_note`，不寫進譯文本身。只有系列風格 `notes = inline`（預設開啟；`ncte style set --notes off` 關閉）時，翻譯請求才允許模型在雙關、文字遊戲、文化指涉無法用譯文傳達時寫一句說明（不寫劇情）。匯出時接在該段後面：「……（註：……）」；人工修改過的段落不附加。`ncte notes list` 檢視、`ncte notes drop` 刪除單一則。採用括號而非彈出式註解（使用者偏好，且 EPUB 2 也能顯示）。
  - 翻譯規則：引號內台詞用符合角色的口語，不用書面語或照搬日文結構；敘述文維持原作文體。
- 不納入快取鍵：既有譯文不受影響，要加註需重翻。

## ADR-026 讀的階段專門找雙關與現實指涉
- 背景（實測）：主角的姓和服飾連鎖店同名的梗。flash、flash medium、sonnet 5.5 翻譯時都沒加譯註，但單獨問 flash「這句有什麼梗」時立刻答對——翻譯時要同時顧十幾條規則，注意力不在找梗；而不給上下文、只問「這些名字有沒有典故」又會列出一堆不需要說明的聯想（與角色同姓的名人、企業）。
- 決定：記憶整理（讀的階段，每個場景都會看）多輸出 `wordplay`：本場景中翻成中文後讀者會看不懂的雙關、諧音、文字遊戲或現實指涉，附單元、原文逐字的詞與引文、說明、建議譯註；程式核對逐字存在後存在 `reader_notes`（重讀場景時取代）。翻譯該單元時附上 `wordplay`，要求先讓譯文本身傳達，做不到且系列允許譯註時才寫 `translator_note`。`ncte notes found` 列出找到的項目與是否已加註。

## ADR-027 本機網頁介面（`ncte gui`）
- 決定：用 Python 標準函式庫的 HTTP 伺服器提供單頁網頁（原生 JavaScript，無框架、無外部資源），直接讀寫系列資料庫；不新增相依套件。
- 安全：只綁 127.0.0.1；只接受 Host 為 127.0.0.1／localhost（防 DNS rebinding）；每次啟動產生隨機 token，所有 API 都要帶（其他網頁無法讀寫書庫）；CSP 只允許同源腳本；一次處理一個請求（SQLite 連線不需鎖）。
- 第一版頁面：書庫、概況（進度、費用、待處理數）、對照審稿（篩選有疑點／說話者未定／譯註與梗／人工修改／逐章；點譯文直接修改，段落外層的排版標記自動保留；可改回機器譯文、刪除譯註）、定名（選項、自填、原文例句、全部採用）、閱讀（故事進度、角色檔案、人物關係圖，共用防劇透滑桿）、名詞與稱呼。寫入都呼叫與指令相同的函式。
- 防劇透：系列資料中較後集數的角色與稱呼不顯示；場景出場角色只用當時已登場的角色比對。翻譯、匯出仍用指令（之後再加到網頁）。

## ADR-028 定名時檢查「名字是稱呼、又與他人重疊」的角色
- 背景（實書）：第 2 集把A的母親建成名為「Aさん」的角色；同學叫A的「Aさん」因此被算成在叫母親，名詞表也多了「Aさん → A太太」，重翻第 1 集時會誤導翻譯。程式能偵測這種角色，但要人看得懂日文才知道怎麼修。
- 決定：定名請求附上這類角色（名字＝另一角色名＋敬稱）與例句，請模型判斷是「另一個人（給描述性名字，例如Aの母／A媽媽）」、「同一人」或「無法判斷」，列為待決定的「角色修正」，不自動套用。選「改名」：角色改用描述性名字（原稱呼留作別名），該稱呼記為與另一角色共用（`form_senses`，之後不會自動歸給任何一人，翻譯時附 `may_refer_to`），用到它的場景重新整理稱呼，該稱呼的名字提案作廢；選「合併」：併入另一角色；也可自填名字或維持現狀。這類角色的名字不再當一般名字提案。

## ADR-029 譯名改變時套到既有譯文
- 決定：定名或稱呼在翻譯後才改時，找出原文含該稱呼、譯文含舊譯法的段落，可直接替換（純名字，免費）或重翻；人工譯文只列出不改（`translation/rename.py`）。只在一個譯名決定時同步名詞表裡含有它的全名與複合詞（名字 → 含這個名字的全名、國名）；某人對某人的稱呼（「〇〇の坊主」→〇〇小子）不會改到那個人本身的名字。

## ADR-030 角色性別（妳／你）
- 背景（奇幻戀愛輕小說 vs 正式版）：約 18 句對女性用了「你」。說話者都對，但角色卡沒有性別，模型只能從當段猜。
- 決定：讀的階段（memory_update）記錄性別，必須附逐字原文。分兩級：`explicit`（引文裡有程式詞表中的性別字詞：彼女、少女、女性、少年、青年…）與 `inferred`（口吻、自稱等）；模型說 explicit 但引文沒有性別字詞時降為 inferred。明確優先於推測；同級互相矛盾時記為 conflict、不提供；人工設定最優先。從證據出現的位置起才可見（防劇透）。翻譯時角色卡附 `gender`（推測的標 `(inferred)`，上下文支持才用「妳／她」）；沒有性別的人物不准憑名字猜。`ncte names gender`／`gender-scan`（為已讀過的書補記，不動其他記憶）。

## ADR-031 程式比對是證據，不是判決
- 背景：三本書中程式的對話標記有 6 次與 LLM 不同（共 82 句明確標記），6 次都是 LLM 對（標記其實屬於隔壁台詞、「とHに声をかけた」把被搭話的人當說話者、「使い続け」被當成說話動詞）。被程式鎖成 explicit 的錯誤說話者還會變成說話範例，污染說話習慣。
- 決定：LLM 對程式的對話標記有異議時，採用 LLM 的說話者、標為 `inferred`（不當說話範例）；兩邊一致或 LLM 未表示時才是 `explicit`。旁白動作與 LLM 強證據衝突時維持 `unknown`（抽查顯示這裡 LLM 也會錯）。同理：稱呼的對象原本由程式依「台詞裡出現誰的名字」決定，現在記憶模型對該場景同一說話者、同一稱呼只回報一個對象時，以模型為準（「Aさん」對母親說）。
- 檢查型規則（證據須逐字存在、ID 須存在）不變：它們只擋捏造，不替 LLM 給答案。

## ADR-032 名字揭曉時合併描述性角色
- 背景：「黒髪の女性」先被建成角色，下一場景名字揭曉，又建了她的全名（別名含黒髪の女性）——分析格式沒有「已知人物原來叫某某」的欄位，台詞、事實、性別分散在兩個角色。
- 決定：`new_characters[].same_as_ref` 指向已知人物時合併；模型沒填時，程式只在新人物的別名正好是**一個**、近期（400 段內）登場、非一般稱呼的描述性角色名稱時合併。新名字與它自己的別名以揭曉位置記錄連結，揭曉前只顯示描述性名稱。合併時一併搬移稱呼、性別、道具、場景狀態與定名提案。
- 同一份請求中，稱呼表有說話者專屬譯法的稱呼，不再同時附上與之矛盾的未確認名詞表譯名；同一暱稱的拼寫變體與加敬稱的形式附上已定譯法（`same_nickname_decided`）。

## ADR-033 讀完後只覆核有爭議的判斷
- 背景：讀的階段是「LLM 判斷、程式檢查」，沒有第二次確認；全部重看會讓讀的費用加倍，而逐段讀查顯示大部分判斷正確。
- 決定：讀完、定名前，把有疑義的項目帶著前後文（前後各 4 段）再問一次（每次最多 25 項）：LLM 推翻程式標記的台詞、旁白動作與 LLM 強證據衝突而成為 unknown 的台詞、只有推測的性別、名字揭曉時的合併。結果不升級為事實：說話者仍是 `inferred`（或改為 `unknown`）；推測性別若沒被確認就刪除（翻譯退回「你」）；合併若被質疑記為待人工確認的問題；被判斷「不是同一人」時，合併帶來的稱呼從該角色移除（不自動搬回台詞）。指多人的描述（〜の二人、〜たち）不會被合併進單一角色。沒有疑義時不發請求。別名附 LLM 標的種類（名字／暱稱／稱號／描述／普通名詞），普通名詞不收；一般詞表只作為檢查。

## ADR-034 不用指令也能用：網頁介面的上傳、翻譯、匯出
- 背景：網頁介面原本只能審稿與定名；匯入、翻譯、續譯、匯出都要用指令，不熟指令的人無法使用。
- 決定：
  - 書庫頁可拖放上傳 EPUB：先做安全檢查並顯示偵測到的系列與集數，由使用者選擇放在哪個系列後才匯入（不自動套用，與指令相同）。
  - 概況頁的「開始翻譯」不提供模型與推理程度選項，用設定檔的預設值（模型比較的結果：gemini-3.8-flash、模型預設的 medium）。開始前顯示無付費試算的估價；預算上限自動設為估價的 2 倍（至少 US$0.5；原為 1.5 倍，見 ADR-035），只用來擋異常（重試循環、推理暴增、程式錯誤），到了會停下並顯示已花費與剩餘估計，按一下提高上限繼續。
  - 翻譯在背景執行緒進行，使用自己的資料庫連線；同時只翻一本。頁面顯示讀、覆核、定名、翻譯、審稿各階段進度與最近的紀錄；暫停在目前的請求完成後生效；程式被關掉時，該次執行視為已暫停，可繼續。需要定名時停下並指向定名頁。
  - 匯出 EPUB（含驗證）並從頁面下載。
  - 設定頁可貼上 OpenRouter 金鑰：存在本機 `.env`（權限 600），畫面只顯示末四碼，API 不回傳金鑰；顯示帳戶與金鑰剩餘額度。
  - `NCTE.command`：在 Finder 雙擊即可啟動（第一次自動建立環境並安裝）。
- 估價的限制：沒有任何實際花費可校正時（全新的工作區），估價偏低（奇幻戀愛那本試算上限 $4.3，實際約 $5.6＋覆核）；在同一工作區翻過書後會用實際花費校正。

## ADR-035 定名預設不暫停
- 背景：奇幻戀愛那本重跑時，模型原本的譯名建議（學院長的譯名、一個暱稱）與正式版一致，人工（照我的建議）改掉反而偏離；暫停等人決定也讓整本翻譯卡住。目標是不懂日文、只用網頁的人也能一路翻完。
- 決定：`context.naming` 預設改為 `auto`：模型的建議直接使用，經程式檢查——人名只有一個字時改用兩個字以上的替代譯名；角色修正（另一人／同一人）模型判斷明確時套用，不確定時維持現狀。名字與稱呼的選擇仍列在定名頁（「可再確認」），之後改了會連同已翻好的段落一起替換（ADR-029）。`review` 保留為選項（暫停等人決定）。
- 預算上限改為估價的 2 倍：只擋異常，正常的估價誤差不會碰到。
- 翻譯中途改了譯名，從下一個場景起生效（每個場景重新讀名詞表），不必暫停。
- 改人名時，也找出「原文沒寫名字、譯文補上了名字」的段落（§1052「〔父親的名字〕如此放聲大笑」）；只對人名做（譯名夠特殊，不會誤換到別的詞）。

## ADR-036 沒有換場標記的長段落由模型決定切點
- 背景：場景在匯入時由程式切：作者的標記（換檔、分隔記號、標題、空行）之外，超過 80 段就硬切；奇幻美食那本 109 個場景中 46 個是硬切，可能切在對話中間，讀的階段判斷說話者時就少了前文。
- 決定：作者的標記仍由程式照切（那不是猜測）。翻譯開始、尚未讀任何場景時，把每段沒有標記的長段落（多個硬切場景相連）交給模型：只送每段開頭 50 字與是否為台詞，請它指出新場景從哪一段開始（時間、地點、視角轉換或一件事告一段落；不切在對話中間）。程式檢查：切點必須在該段落內、不能是跨段台詞的後半、每個場景至少 12 段、不超過上限的 2 倍；不合格就保留程式的切法。已讀過的書不重切（場景編號已在使用）。`context.scene_breaks = "program"` 可關閉。
- 程式的備案也改了：硬切等到前後都是敘述的位置（最多延後 30 段），不再切在台詞旁。

## ADR-037 程式比對出的稱呼由模型歸類
- 背景：稱呼表大多由程式產生：某人的台詞裡出現另一個角色的名字或別名，就記成「他這樣叫那個人」。奇幻戀愛那本 141 筆中 108 筆如此，常見錯誤：轉述別人的叫法（「會叫我『閣下』的人只有一個」）記成自稱、談論傳說中的「英雄」記成自稱、「欲張り最強セット」因「最強」是別名而記成稱呼。這些會進到定名提案與翻譯時附上的稱呼資料。
- 決定：讀完後的覆核（ADR-033）一併處理：每筆程式比對、尚未經模型確認或人工決定的稱呼，附上最多兩句台詞與前後文，請模型歸類為 `address`（當面叫）、`mention`（提到不在場的人）、`self`（自稱）、`quoted`（轉述別人的叫法）、`unrelated`（字面相同但不是指那個人）。存在 `address_usage`（以說話者、對象、稱呼為鍵，重新整理場景時不會遺失）。`quoted`、`unrelated` 不再出現在翻譯資料與定名提案；自稱不再提案譯法（就是名字本身的譯法）；`mention` 在翻譯資料中標明。已讀過的書用 `ncte names address-check` 補做。

## ADR-038 翻完後的讀者視角檢查
- 背景：校園日常那本的主角和日本一家服飾連鎖店同名，主角因此不喜歡自己的姓；譯文保留了平假名卻沒說明，不懂日文的讀者看不懂。雙關與文化梗種類太多（讀音、寫法、品牌、作品、習俗），讀的階段列舉不完。
- 決定：整本翻完、審稿之後，模型只讀中文（每次約 120 段，附主要人物的中文名與性別），以不懂日文的台灣讀者身分指出會卡住的地方：沒交代的指涉、看不出的雙關、嚴重翻譯腔、口吻或你／妳不一致、前後矛盾。程式附上提示（譯文保留了假名、原文在談論字詞本身）。中、高程度的問題帶著原文與前後文交回翻譯：能改寫就改寫，譯法無法傳達就加譯註，其實沒問題就維持原譯；修改後照常經程式檢查。已翻完的書用 `ncte reader-check`。`context.reader_pass = false` 可關閉。

## ADR-039 人物關係由事實歸納
- 背景：人物關係圖原本只畫「同一場景出現」的次數：奇幻那本的女性職員和女主角父親從未有交集，只因一個太粗的場景（回顧＋抵達考場）就被連在一起；圖上也看不出兩人是什麼關係。
- 決定：讀完、覆核後，把主要人物（最多 30 人）與提到他們的事實（附原文證據）交給模型，歸納關係（父女、未婚夫妻、師生、前世宿敵…），每條必須引用支持它的事實；程式只保留兩人都是已知角色、且引用的事實存在的關係，並以最早那條事實的揭露位置作為「從這裡起讀者才知道」。關係圖預設改為「關係」模式（線上標出關係名稱，拖動「讀到」滑桿時未揭露的不出現）；「一起出場」「誰怎麼叫誰」保留。翻譯時的角色卡附上同場人物之間已揭露的關係，幫助判斷說話的口吻與稱呼。已讀過的書用 `ncte names relations`。
- 角色檔案的「自稱」改為統計台詞裡的第一人稱（俺、わたし、ボク…）；原本的「自稱」列改名為「提到自己」。

## ADR-040 敘述人稱
- 背景：第三人稱的奇幻書中，日文省略主語或用「こちら」時，翻譯在 11 處補成「我」，像是突然換成男主角在說話（正式版皆為男主角的名字）。翻譯每次只看約 1,400 字，看不出整本是第幾人稱，尤其周圍都是主角用「俺」說話時。
- 第一版（整本）：從原文統計台詞以外的敘述出現第一人稱代名詞的比例，低於 3% 為第三人稱、高於 10% 為第一人稱，其間不判斷；翻譯資料附上 `narration`，提示詞要求第三人稱時敘述不寫「我」；第三人稱的書敘述出現「我」標記交給審稿。
- 決定（逐場景，像譯者一樣）：讀的階段由模型判斷每個場景的敘述方式（`first`＋敘述者，或 `third`＋視角人物），附依據；輸入附上一個場景的判斷與程式統計（本場景敘述段落數、含第一人稱的段落數）。程式檢查：第三人稱但敘述含第一人稱超過 15%、或第一人稱但低於 2% 時記為矛盾，交給覆核（ADR-033）再判斷。翻譯時附這個場景的 `narration`（人稱、視角人物或敘述者的中文名）；沒有判斷或仍矛盾時用整本統計。第三人稱場景的敘述出現「我」標記交給審稿。
- 原文那段敘述本身有「僕」「私」（角色用自己的話想事情，例：「そうだ僕は知っていたのだ」）時，譯成「我」是對的，不標記。
- 敘述者自稱（第一人稱）：讀的階段同時列出敘述者在敘述裡稱呼自己的詞與中文譯法（`self_forms`，例：古風自大的自稱保留口吻，一般的「私」譯「我」）；同一位敘述者的同一個詞以第一次的決定為準、之後場景照用（輸入附 `established_self_forms`），程式只保留本場景敘述裡真的出現的詞，反身的「自分→自己」不算。翻譯時隨 `narration` 附上；敘述有這個詞、譯文卻沒用固定譯法（或把要譯成「我」的詞照抄）時標記交給審稿。起因：以貓為敘述者的古典小說，抽驗 30 段中自稱前 12 段譯「我」、中間 12 段譯「吾輩」，讀者檢查只修了其中兩段，混用仍在；改後 17 段一致。

## ADR-042 同一個系列一次只讓一個程序翻譯
- 背景：fal 實測時，同一個任務被指令列與網頁同時執行。網頁看到狀態是「執行中」但不是自己在跑，就當成上次中斷、顯示「繼續」；按下後把所有「執行中」的工作改回「待做」，兩邊送出相同的請求（完全相同的請求 52 次，約 US$1.6）。
- 決定：系列資料庫旁放一個 `run.lock`，任何任務開始或繼續時先用作業系統的檔案鎖（flock）取得；拿不到就在改任何東西之前停止，告訴使用者是誰（指令列／網頁、pid、哪個任務、何時開始）。程序不管怎麼結束，系統都會釋放這把鎖，所以當掉的任務仍可續譯，不會被誤認成還在跑；不需要心跳或判斷程序是否存活。網頁在別的程序持有鎖時顯示「另一個程序正在翻譯」，不提供「繼續」，開始與繼續也會被拒絕。範圍是整個系列（同系列的書共用記憶，同時寫入會互相干擾），與網頁「一次只翻一本」一致。
- 指令列的任務標頭也顯示連線方式（`via=OpenRouter`／`via=fal`）：`.env` 的 `NCTE_LLM_PROVIDER` 會套用到指令列，原本看不出來。

## ADR-043 提示詞快取
- 背景：Gemini 請求的輸入約占費用三成，每次都重送同樣的系統提示詞，但快取命中率幾乎是 0（抽驗 122 個請求只有 3 個部分命中）。實測（2026-10-15）：同樣的系統提示詞送三次，不加標記全部照全價；加上 `cache_control` 標記並送到 Google AI Studio，從第一次起就讀快取，那幾次請求只要原本的 1/6–1/9；送到 Vertex 則加了標記也不會快取。
- 決定：直連 OpenRouter 時，系統提示詞以內容陣列送出並加上 `cache_control: ephemeral`；變動的資料留在後面的 user 訊息。Google 模型優先送 `google-ai-studio`（`allow_fallbacks: true`，它出問題時照常改用其他端點）。引擎內部的請求格式不變（測試替身、請求雜湊、費用紀錄不受影響）。fal 會不會轉送這兩個設定尚未驗證，fal 路徑維持原樣。
- 效益：實際翻譯請求中系統提示詞約占輸入的 16%（1,887／11,675 token），所以總費用約省 4%，比原先估的少；其餘輸入（角色卡、記憶、前後段落、原文）每批都不同。要再省得調整提示詞與資料的排列，把整本書固定的部分放在前面（會改變模型看到的順序，需抽驗）。

## ADR-044 一個場景一個翻譯請求；場景切點由模型決定
- 背景：翻譯原本每 1,400 字一批（最初規格的預設值，沒有從翻譯角度檢討過）。場景中位數約 2,800 字，所以一個場景常被切成 2–3 批、切點可能落在一段對話中間，每批只看得到前 2 段、後 1 段原文。譯者是讀完整個場景再動筆。
- 決定：context 模式每個場景一個請求（`translation.scene_max_chars`，預設 6,000 字）；超過的場景切成最少、最平均的幾段，切點選最近的「兩段敘述之間」，每一段都附整個場景當參考。場景本身由模型決定切點：作者的記號（章節、分隔符、空行）照切；沒有記號的段落交給模型，包括因為太長而要切的地方（輸入附每段的結尾與字數、每個場景的字數上限）。程式只檢查（切點存在、場景不過短；前一段以「――」「、」結尾、句子接到下一段的切點附前後文交回模型再看一次，模型的答案為準）；模型失敗時才照長度切。強制重讀整本時重新選切點；`ncte scenes --rebreak` 給在 ADR-036 之前切好的書。重切後範圍改變的場景，讀的結果（事實、摘要、物品、讀者筆記）一併清除，下次執行重新讀；台詞跟著段落換到新場景。
- 同時：送給模型的編號改短代號（`P1`/`C1`/`F1`/`Q1`，只在編號欄位換回，譯文與說明從不更動）；場景分析每句台詞用短欄位名，與程式標記一致時不列候選；各步驟可設不同推理程度或推理 token 上限（`openrouter.stage_reasoning`）；翻譯的系統提示詞把每次都相同的規則放前面並快取，本批資料需要的規則接在後面。
- 驗證：離線測試（342 passed）。品質與費用待儲值後抽驗（同一章新舊比較、讀取格式、推理程度）。

## ADR-045 敘述者卡、讀時記錄的關係、一對一歸納、角色印象、以關係為中心的關係圖
- 背景：沒有名字的第一人稱敘述者不是角色，關係、事實、別人怎麼叫他都沒地方放（古典小說前 2 章 15 個角色只有 1 條關係）；關係在讀完後才從事實裡用「完整中文名」回頭找，189 筆事實有 79 筆提到對方時只寫短名或代號而對不上，重讀時整批蓋掉；角色檔案沒有對人物的整體印象；關係圖沒有中心，「對等關係」用一張詞表判斷。
- 敘述者卡：讀的時候，第一人稱又不知道是誰的場景，模型填 `new_narrator`，程式建立「（敘述者）」卡（只在這一集，不跨集），之後的場景把它當成已知的敘述者；他的台詞、事實、關係、別人怎麼叫他都記在卡上。讀完整本後在覆核裡問一次：是不是某個有名字的角色（附事實、稱呼、台詞）；是就合併，名字在原本出現之前仍不顯示（ADR-032 的揭曉機制）。翻譯時卡上標明「這是敘述者，譯文裡就是『我』」，不給可以照抄的名稱；譯文出現「敘述者」由程式標出、模型確認。場景的敘述者與說話的人都算在場（第一人稱的敘述者很少在自己的敘述裡被叫名字）。
- 關係：記憶整理時記下原文寫明的關係（雙方用角色代號、附逐字原文、分身分與情感），事實的另一個人也用代號（`object_ref`）。讀完後，程式為每一對有材料的人物（讀時記錄、兩人都有的事實〔代號、全名、短名、別名〕、互相的稱呼、一起說話的場景數）整理材料，每次請求幾對；模型只能引用這一對自己的材料；從最早的依據開始顯示；模型說後來的關係取代先前的（宿敵 → 未婚夫妻）就把先前的結束在那裡；有材料卻沒回答的人物對再問一次。重跑只換掉模型產生的關係，人工設定的保留。不用規則推導關係（例如父親＋訂婚＝未來岳父）：原文沒寫的不畫。
- 角色印象：讀完後為主要角色整理個性、口吻、在故事裡的定位（不寫結局或後期揭露），附依據的台詞與事實；口吻放進翻譯時的角色卡，定位不給翻譯；`ncte names impressions` 給已讀過的書。
- 關係圖：中心是關係最多的人（另一個人多兩條以上才換，點人可換），其他人照離中心幾步排成一圈一圈、靠近與自己相連的人；滑桿位置顯示當時成立的關係；兩邊角色相同寫在中間、不同寫在兩端，不再用詞表。角色檔案多「角色印象」與「人物關係」（附原文依據、類型、是否推測或人工）。


## ADR-046 親屬稱呼對到既有人物、群體與成員、複數第二人稱看整群人
- 背景：妹妹敘述的番外篇裡「姉ちゃん」被建成另一個角色「姊姊」，其實是前面已經有名字的主角；「跟班兩人」「跟班」兩張群體卡重複，個人（瓦爾克、盧卡斯）只得到「同伴」；對一位女性說「お前ら」（指她帶領的軍隊、她的國家）被譯成「妳們」。
- 讀的時候：已知角色卡附上到目前為止的關係（「X的姊姊」，只算在這一段之前成立的）；提示詞要親屬或關係稱呼先看說話者、敘述者的關係，對得上就用那個角色，不要另建。
- 讀完後覆核（模型判斷，程式只挑出要問的卡）：只用一般稱呼、不在名詞表人名裡、有台詞或關係的人物，附第一次出現的前後文與別人怎麼叫他，問是不是某個有名字的角色 → 是就合併（名字在原本出現之前不顯示，同 ADR-032）。群體卡（「〜兩人」「〜們」）問成員是誰、是不是和另一張群體卡同一群 → 同一群就合併，成員記在 `group_members`（migration 20）。每次最多 12 張。
- 關係：群體的關係材料也交給各成員的人物對，標明「關於群體『…』」，由模型判斷對這個人是否成立；不用規則把群體關係直接複製給成員。
- 翻譯：複數第二人稱照它指的那群人：全是女性才用「妳們」，其餘「你們」；對一個人說、卻指她所屬的整群人時看那整群人。原則寫在提示詞，不列字詞表。
- 補充（同日）：群體成員在讀的時候就記（記憶整理的 `groups`，要附逐字原文；重讀這個場景會換掉），已知的群體卡附上成員給之後的場景；記關係時，原文給群體的身分也是成員的身分。整理關係時，成員的人物對除了群體的關係紀錄與事實，還附原文裡群體和對方一起出現的段落（程式用名字比對找段落，意思由模型判斷；最多 3 段，可被引用為依據）。覆核問到的卡也包括有稱呼紀錄或群體成員紀錄的卡，最多 24 張。

## ADR-047 被擋時各步驟都分段、複數第二人稱的程式檢查、關係補問、接受通行譯名
- 內容過濾：切場景、覆核、人物關係、角色印象、定名被擋時，和讀取、讀者檢查一樣切成兩半重送，直到過了或小到放棄（記一筆 `*_blocked`）。定名有幾份清單時切最長的那份，其他清單只跟前半一起送，不會重複問。
- 複數第二人稱：讀的時候記下這句是對兩人以上說、而且每個人的性別都是原文寫明的，譯文就照他們檢查——全是女性卻只有「你們」、有男性卻只有「妳們」時標出，交給規則確認與審稿。對一個人說的複數（指她的軍隊、國家）由翻譯判斷，不檢查。
- 關係補問：沒回答的人物對，除了讀時有紀錄的，也補問「有互相稱呼，又有事實、群體原文或一起出現三個場景以上」的（「義父さん」加一條事實，三次有兩次沒回答）。
- 外部知識：模型知道的通行譯名（名著書名、知名角色名）可以用，不算「原文沒有的資訊」。
- 規則誤報維持由規則確認先篩（ADR-044），確認有問題的才交審稿。

## ADR-048 整理關係時附上兩人一起出現的原文
- 背景：關係只靠讀的時候記一次。需要推一層才知道的關係（兄長與同住的人被祖父母嫌「確定沒有孫子」），同一場景讀 7 次只有 1 次記到；記憶整理的輸入幾乎相同（約 1.12 萬 token），模型 7 次有 6 次沒有推理。改寫記憶整理提示詞（依據要選讓關係成立的那段）對照後沒有改善，撤回。
- 做法：整理關係時，每一對人物另外附上原文裡兩人一起出現的段落：段落裡點名其中一人，另一人在前後一段內被點名或正在說話；附前後各一段，台詞標出說話者。優先挑「被談論時另一人在對話裡」或「兩人同段被點名」的段落，分散在全書，每對最多 6 段，長段落只取名字附近。找段落是名字比對，意思由模型判斷；段落可被引用為依據。
- 代價：整理關係的請求約多一成到兩成（兩本各約 6.5 萬字）。

## ADR-049 人物關係與覆核預設用 high 推理
- 背景：設定 medium 時，模型常常自己選擇完全不思考（整本跑的場景分析 73 次有 45 次、記憶整理 51 次、人物關係 7 次有 4 次推理為 0）；指定推理 token 上限（`max:2000`）也一樣是 0，上限只是上限。high 才會真的思考：需要推一層的關係，兩次讀都記到。
- 決定：人物關係與覆核（讀完整本後、看全書材料做判斷，一本只有十幾次請求）在模型提供 high 時預設用 high（實測人物關係每次推理約 6,000–14,000 token，一本從約 US$0.09 變成 US$0.21–0.27，覆核另計；先前估 +US$0.05–0.1 偏低）；使用者自己設定的步驟推理優先。其他步驟維持 medium；記憶整理是否用 high 另做比較（一本約 +US$1.5）。

## ADR-050 同一人的不同身分是一種關係類型
- 人物關係多一種類型 `same_person`：兩張人物卡是同一個人的不同身分（分身或虛擬形象、秘密身分、化名、不同時期或前世的自己），兩個身分在故事裡各自行動。是否成立由模型依原文判斷，照一般規則分確定（原文寫明）與推測，從揭曉或首次暗示的位置開始。
- 只是名字還不知道或換了叫法的（沒有名字的描述、敘述者卡、綽號、親屬稱呼）照舊由覆核合併成一張卡。
- 關係圖照類型畫雙線（推測為虛線雙線），不看關係名稱的字面；這類標籤在人多時也一律顯示。

## ADR-051 全書對照校稿
- 背景：讀者檢查只看中文，抓不到「讀起來通順、意思卻錯」的句子；審稿只看被標出的段落（約 1%）。抽驗 720 段，對照校稿抓到 5 句現有步驟都沒標出的誤譯（固定句型照字面譯、意思相反、對當面的人用第三人稱）。
- 做法：翻完後、讀者檢查之前，逐章（每次約 60 段）把原文、譯文、讀的時候判斷的說話者，與這一段出場人物的譯名、性別、口吻交給模型，只回報真正的錯誤：意思、漏譯、加譯（含提前寫出還沒交代的事）、說話者或對象、語氣、口吻、體例。低嚴重度不處理；其餘寫成疑點，連同說明與建議改法交回翻譯步驟依原文重翻（說明不對就維持原譯），再經程式檢查。被內容過濾擋下時切半重送。
- `ncte proofread` 給已翻好的書（可用 `--unit-id` 限定範圍）；`context.proofread` 可關閉。

## ADR-052 讀音用專用記號，不和原文的《》混用
- 背景：抽取 EPUB 時把 ruby 攤平成「漢字《かな》」，和原文本身的《》（書名號、特殊名稱）共用符號；刪除讀音時連原文的《亡雄の旅団》也刪掉，對照校稿因此誤以為譯文多加了字，名字比對與程式檢查也受影響。
- 做法：讀音改存成 Unicode 為行間注音設計的三個字元（U+FFF9 漢字 U+FFFA かな U+FFFB），書本文字不會出現，原文的《》永遠是原文。送給模型時集中轉成熟悉的「漢字《かな》」；比對文字時去掉讀音（也去掉模型引用時帶回的「漢字《かな》」）。
- 已匯入的書開書時升級一次：從存放的 EPUB 重新抽出段落，以舊寫法顯示後與原本完全相同的才換成新記號與新雜湊，譯文跟著換，不必重翻；其餘不動。新匯入的書直接用新記號。

## ADR-053 全書體例：標點由程式統一，敬稱與說話習慣由模型定
- 背景：同一本書裡破折號混用（日式「――」「──」與「——」）、中文旁出現半形「!?」「,」；同一種敬稱有時譯出有時省略；角色的固定語尾沒有固定譯法。引擎原有的系列風格只在人工設定時才用。
- 標點：像排版一樣，每筆機器譯文存入前統一成臺灣出版慣例（破折號「——」、刪節號「……」、中文旁的 ！？，：；為全形），只動符號、不動文字，佔位標記與拉丁文字段不動；人工修改的不動。`ncte recheck` 也套用到已存的機器譯文。
- 敬稱與說話習慣：讀完全書、角色印象之後、定名之前，模型看書中的稱呼與次數、主要角色分散全書的台詞與程式統計的反覆句尾，選定敬稱處理方式（自然／譯出／省略）、主要角色真正的說話習慣與固定中文表現、最多 6 條本書體例，寫入系列風格（標記為自動）；人工設定過的系列風格不覆蓋。定名、翻譯、對照校稿都會拿到。`ncte style auto` 給已讀過的書。
- 抽驗後修正：(1) 格式標記裡只有符號的一段（例如「啊⟦1⟧!?⟦/1⟧」，原書的縱中橫）以標記兩側的字判斷是不是中文語境，中文語境包含 CJK 符號與全形字元區塊（「」、。　～ 等），不再逐一列舉；(2) 模型把角色語氣寫成體例規則（「關西腔以辛辣、帶壓迫感的口吻呈現」），譯者為了演出語氣刪掉內容、改了說話對象。通則：體例規則必須是具體譯法，語氣只放在角色口吻與說話習慣；翻譯提示寫明風格只決定怎麼說、不改變說了什麼（內容、人稱、說話對象照原文）。
- 第二輪抽驗後修正：體例原本只看原文台詞，自己替暱稱另定譯法（和定名、現行譯文都不同）。通則：人名、暱稱、稱號的中文由定名決定，體例拿到已定的譯名照用、不另定；台詞已有譯文時一併附上，說話習慣的固定表現沿用現行譯法。
- 第三輪：標點之外再統一兩件排版——全形英數字一律轉半形（ＯＫ → OK；術語表比對時譯名也先轉半形，不會誤報），兩邊都是中文字或全形符號（含 ☆♡♪）之間的半形空白轉成全形「　」；中英、中數之間的空白不動。體例的輸入除了分散全書的台詞，每個反覆語尾再附一句例句，讓特色台詞不會因為取樣漏掉。

## ADR-054 刻意的說話方式要譯出效果
- 背景：抽驗時口齒不清的台詞被譯成標準說法、刻意模仿運動社團腔的招呼被譯成普通問候，下一句的吐槽就接不上；對照校稿也不認為這是錯。
- 決定：翻譯提示加一條通則——原文刻意的說話方式（口齒不清、結巴、拉長音、口誤、方言、外國腔、模仿某種人的腔調等），中文要做出讀者感覺得到的對應效果，寫法可以不同；原文是標準說法的地方不要自己加；前後文有人吐槽、模仿或評論某句話的說法時，那個特徵要在譯文裡看得出來。對照校稿把「刻意的說話方式被譯成標準說法」「後文的反應接不上」算進 voice 類的錯。只列例子、以前後文為準，不是逐項的規則清單（最初逐項列舉時，模型把它當成封閉清單，漏掉模仿腔調）。
- 時態這類小偏差不另加提示：改變意思的已在 meaning 類。

## ADR-055 修正要對照原文驗收；沒看到的不算看過
- 背景（審查 `docs/audit-2026-10-17.md`）：審稿、對照校稿、讀者檢查之後的重譯只要通過程式檢查就算修好，該單元所有開著的問題一起結案；重譯時模型看不到現行譯文；被內容過濾擋下的段落被算成已審，原本的嚴重標記被清掉。
- 決定：
  1. 重譯帶現行譯文（`review_feedback[].current_translation`），只改原文支持的錯。
  2. 每個修正對照原文驗收一次（`fix_check`）：`fixed`、`issue_invalid` 才結案，而且只結案送去修的那幾筆問題；`still_wrong`、`undecided`、檢查失敗都留著，新譯文 `needs_review`；修正引入新錯時不採用（`rejected_fix`），書裡留舊譯文。不重試到通過為止。`review.fix_check: false` 時修正寫入但永遠記為未驗證。
  3. 問題記在它針對的譯文版本（`qa_findings.translation_id`，migration 22）；清除只清到被看過的那一版。
  4. 審稿、校稿、讀者檢查只把真的送到模型、沒被擋下的段落算進統計；被擋、失敗的段落不清除任何問題，job 標 `blocked`／`failed`／`partial`。
  5. 人工譯文不被機器修正覆蓋；`ncte recheck` 不因程式規則沒找到問題就結案語義問題。
  6. 「可驗收」與「可匯出」分開：`reports/acceptance.py` 逐項列出還缺什麼，匯出時一併報告；可驗收不等於品質合格。

- 補充（2026-10-19，review 後的修正）：只校稿（`ncte proofread`）、只做讀者檢查（`ncte reader-check`）的執行也為這一步建一筆 job（target 為書），可驗收照常看該步驟最後一筆 job；原本不記 job，被擋一段變 partial 後用指令整本重跑也翻不回來。加 `--unit-id` 時不記 job：那不是看過整本，記成 partial 會把原本已完成的書打回未完成（第 2 節修正時改）。校稿與讀者檢查每完成一批（含該批的重譯與修正驗收）把進度寫進 `jobs.checkpoint_json`（`done_until_ordinal` 與累計統計）；暫停（網頁按鈕）或程序被關掉時 job 留在 running，續跑從下一批接，前面的批次不再送。覆核、人物關係、角色印象在每批之前也檢查暫停；關係與印象是全部問完才寫入，中途暫停時這次問到的不寫入、續跑重問整步。

## ADR-056 同一個故事位置只有一套名字；推測與觀點跟著資料走
- 一個步驟送給模型的任何欄位（人物卡、說話者、說話對象、稱呼表、敘述視角、校稿的人物卡）都用 `visibility.visible_names` 取名字；後文才揭曉的名字不再從稱呼或視角帶回前文。
- 事實與關係轉成文字給後續步驟時保留觀點與確定程度（`qualified_fact`：「〔某人認為〕…」「〔敘述者的說法〕…」「…（推測）」；推測的關係附 `certainty: inferred`）。推測歸屬的台詞在體例中標 `guess`，不可只憑它定口癖。
- 發話標記：笑、微笑、苦笑只有用「と」接在台詞後才算；另起一段是反應，只是線索（可能是聽者的反應）。
- 記憶整理拿到相關的舊事實與 id（`known_facts`），區分狀態改變、被推翻、角色認知改變；角色曾經相信的事，不會因真相揭曉而被別的事實撤回。

## ADR-057：章節依目錄、場景由模型在章內分批切（2026-10-17）
- 背景：程式依檔案、標題、空行、長度切場景，空行與換檔常在同一場對話中間切開且不會再合併；模型只補切作者沒分段的長段落，只看每段開頭 50 字。
- 決定：章節依目錄項目指向的段落（沒有目錄時由模型標出新章）；章內由模型分批切場景，每批重疊最後一個未結束的場景，作者標記只是候選；每個換場點記類型與是否需複核。已用舊切法讀過的書不改（避免付費重讀）。
- 後果：每本約 20–30 個切場景請求（gemini-3.8-flash 約 US$0.4–0.8）；場景變長、碎片變少；回憶等類型可供記憶與讀場景使用。


## ADR-058：事實與關係記下成立的時期（2026-10-17）
- 背景：整本模擬（轉生作品）中，同一人的前世與今世共用一張卡，「前世部下的長官」與「今世母親的兒子」並列，事實看不出先後；前世與今世的「母親」被合併成一張卡。
- 決定：事實、讀場景記下的關係、全書關係都有 `period`（「前世」「三年前」；空字串＝故事當下），每個後續步驟顯示成「〔前世〕…」「前世：宿敵」；回憶場景會把 `scene_kind` 告訴記憶更新。字面相同但其實是另一個人時，讀場景填 `other_person`，程式另開一張「母親（前世）」卡，不合併。
- 後果：不只轉生作品，回憶、時間跳躍的作品也適用；時期由模型判斷，沒填就是當下（舊資料不受影響）。

## ADR-059（2026-10-18）：模型讀書，程式整理與核對
- 背景：程式用動詞清單、句型、字詞清單判斷文字的意思（誰說的、是不是同一人、算不算稱呼、是不是群體、性別是否寫明），而且常常凌駕模型。抽驗看到的錯誤多半出在這些規則：被動「言われた」、否定「答えない」被當成發話標記，聽者的反應被當成說話者，一段寫了兩個人只抓第一個名字。日文寫法太多，規則補不完；模型讀上下文本來就懂。
- 原則：**模型讀原文、做判斷，回傳 JSON；程式只做結構、整理、核對證據存在、可見性、預算與流程**。程式核對的是「證據字句確實在原文、位置對得上、id 有效」，不判斷意思。有疑問交給既有的覆核（verify）帶前後文再看一次；不重問到同意為止。
- 改法：
  1. 說話者：拿掉程式的發話標記判斷與規則合併（`dialogue.detect_tags`、`speaker.resolve` 的規則）、也不再把程式猜的說話者當提示給模型。模型每句回答說話者、對誰說、確定程度；標「明確」時附原文裡的發話字句（例：「とミナは言った」），程式核對它逐字在台詞所在或相鄰段落、且含該人物的名字或別名，對不上就記為推測。跨段未閉合的引號仍由程式找出（結構），延續段沿用開頭的說話者，模型給了不同答案時交覆核。口吻範例庫只收核對過的「明確」台詞。
  2. 稱呼：拿掉程式在台詞裡比對「名字＋敬稱」自動建立稱呼（`address.harvest_scene`、`address_observations`），只用記憶更新回報、附逐字證據的稱呼；覆核不再逐一分類程式找到的稱呼。
  3. 名稱連結與身分：拿掉「A。通称B」樣式自動連結（`entities.detect_links` 在讀場景時自動執行）與「描述＋400 段內出現名字就合併」（`scene._revealed`、`_is_description`）；只用模型的 `same_as_ref` 與 `name_links`（都附證據）。
  4. 字詞清單：別名照模型的 `alias_kinds`（不再用普通名詞清單刪）；群體由模型標記（新人物加 `group`，取代「〜たち」「〜二人」樣式）；性別「明確」只核對證據句逐字存在（不再要求含清單上的字）；譯名表候選照模型判斷，程式只擋空白與單字。品質檢查（`qa/rules.py`）的清單是「標出可疑」不是決定，保留。
  5. 場景：章節依目錄（結構）；章內由模型切場景（ADR-057）。拿掉程式刪除「距離不到 3 段」的換場點（改寫進提示詞），模型的場景太長時不再由程式硬切，改為場景完整、分段讀；跨段台詞中間不能換場仍由程式擋（結構）。拿掉舊路線：ADR-036 的長段落補切（`scene_breaks`）、依空行／長度的程式切法（只在模型切章失敗時當備援、標為不確定）、`lone_headings`。
  6. 舊書：工作區的書都是測試資料，不做相容；拿掉一次性的升級程式（讀音格式升級等）。舊書要重新匯入、重讀。
- 保留：目錄與檔案結構、占位標記、讀音、標點統一、證據逐字比對、可見性、預算、工作狀態、品質檢查規則（只標出、重要的交模型確認）、敘述人稱統計（只當提示與檢查）。
- 後果：模型呼叫次數不變；讀場景每句「明確」多一小段原文（輸出約多 5–10%）；覆核少了程式找到的稱呼要分類。程式找到、模型可能漏掉的東西（少見的稱呼）需要抽樣確認。
- 實作（2026-10-18）：說話者由模型回答，「明確」附發話字句、程式核對它在台詞所在段或前後只有敘述的段落、且寫出該人物（`speaker.resolve`）；程式的發話標記與規則合併、`program_speaker` 提示都拿掉。模型不確定（列了候選但沒答案、證據核對不過、長台詞延續段答了另一個人）標「待覆核」，覆核依這個標記挑。稱呼只用記憶更新回報的（附 `usage`），程式把它連到證據所在的台詞；說話者改了，稱呼照資料跟著移動（`address.follow_speakers`），不再比對文字；`ncte names address-check` 移除。名稱連結只用模型的；`ncte names detect` 與讀場景時的樣式連結移除。身分揭曉只用模型的 `same_as_ref`；描述語、群體由模型標（`alias_kinds` 的 `description`、新人物 `group`，`characters.is_group`，migration 27）。性別、譯名表候選照模型判斷。場景：一律依目錄分章、模型章內切；程式不再刪短場景、不再硬切長場景，長場景分段讀（`ContextOrchestrator._read`）；ADR-036 的補切（`scene_breaks`）、`segmentation()` 舊書分流、`lone_headings`、讀音格式升級移除。
- 舊書：工作區既有的書需重新匯入、重讀（不相容）。
- 補充（2026-10-18，審查第二輪）：說話者證據的核對不解析日文：只核對模型引用的字句逐字在這一段（去掉引號內容）或前後只有敘述的段落裡、且寫出這個人的名字或敘述者的自稱；一段裡有兩句台詞時，字句屬於哪一句是模型的判斷。曾試過「以『と』開頭的屬於前一句」的位置規則，反而讓「ミナは「…」と言った」這種最常見的寫法核對失敗。模型把別句的發話句、被動或否定句說成明確，由抽樣抽查「明確」的台詞與對照校稿發現。

## ADR-060（2026-10-18）：角色印象分段；說話對象的確定程度
- 背景（開發指示第二節）：事實、關係、場景摘要早已有範圍（揭露位置、時期、觀點、確定程度），唯獨角色印象（個性、口吻、定位）是一份「讀完全書」的整理，翻譯每一場都送同一份：人物成長、偽裝前後、不同時期的口吻被混成一份，後期的特徵可能被帶到前期。說話對象（`to`）只有人選，沒有確定程度。
- 決定：
  - 角色印象可以分段（migration 30，每段一列）：模型通常只給一段，口吻或個性明顯改變時才分段，每段填 `from`（從哪一句或哪件事實開始成立）與 `period`（另一個時期）。程式記下開始位置與依據裡最晚的位置。翻譯、校稿取「這個位置已經開始」的那一段（第一次出場、還沒有任何一段開始時，用最早那段的口吻當基礎）；個性與定位等依據都出現才顯示；另一個時期的口吻另列，只在本場寫那個時期時用。體例看全部段落；網頁列出每段的範圍。
  - 說話對象的確定程度（migration 29）：模型回報 `to_status`（原文寫出對誰說是 explicit，從場面推斷是 inferred）。翻譯遇到推斷的說話對象，上下文也支持才照他的性別寫你／妳；程式的你／妳檢查只在說話對象是原文寫出的時候才檢查。
  - 覆核的身分、群體、敘述者項目，指紋只看這張卡自己的資料，不看全部候選卡（書裡新增人物卡不會讓所有身分項目重問）。

## ADR-061（2026-10-18）：估價涵蓋每個步驟，並給上限
- 背景：試算只算翻譯、讀場景、記憶整理三個步驟；切場景、覆核、人物關係、角色印象、體例、定名、校稿、讀者檢查、修正驗收都沒算。兩本各 300 段的抽樣裡，沒算到的占實際花費 34–37%；校稿改成推理 high 後更多。網頁的預算上限是估價的 2 倍，實際上只剩約 1.2 倍的餘裕，整本可能在正常情況下撞到上限。用模型最大輸出量當推理量估「上限」則高出實際 9–18 倍，沒有參考價值。
- 決定：
  - 每個步驟都估。依花費跟著什麼走分兩類：讀段落的步驟（翻譯、讀場景、記憶整理、切場景、校稿、讀者檢查）以它讀的字數算；一本一次的步驟（覆核、人物關係、角色印象、體例、定名、確認、修正驗收、審稿）以該次執行翻譯的字數算。
  - 同模型、同推理設定、同連線方式的過去執行校正：一般值＝最近 10 次的總花費除以總字數；上限＝其中每字最貴的一次 × 1.2。小於 5000 字的執行不算（每次請求的固定開銷會讓每字成本看起來很貴）；複製的工作區帶著同一次執行，只算一次；一本一次的步驟只採用有讀書的執行（只重跑校稿的不算一本）。
  - 沒有紀錄的步驟依抽樣中占「翻譯＋讀」的比例估（校稿依推理設定分 medium／high），上限再乘 2，標為「抽樣占比」。翻譯與讀都沒有紀錄（新模型）時用字數的 token 模型估範圍。
  - 網頁顯示「約多少、最多多少」，預算上限＝最多 × 1.1（至少 US$0.5）。指令列 `--dry-run` 列出每個步驟。
- 驗證（2026-10-18，以實驗工作區的紀錄估三本前 300 段）：奇幻美食那本 實際 0.707／估 0.58、上限 0.92；奇幻戀愛那本 0.714（校稿 medium）／0.64、1.04；第一人稱奇幻那本 0.598（校稿 medium）／0.92、1.48。實際都在上限內，一般值誤差約 ±25%，文字較密的書會估高。整本推估約 US$8–11。
- 取代 ADR-034 的「預算上限＝估價 × 2」。

## ADR-062（2026-10-19）：Claude 方案當模型（`claude` 來源）；agent 逐題回答（`ncte agent`、MCP、skill）
- 背景：使用者希望不再經 OpenRouter 付費，改用自己的 Claude 訂閱。先在獨立的 ncte-agent repo 驗證：引擎每個請求變成任務，由 Claude Code 的非互動模式（`claude -p`）逐題回答。同一本書整本跑三種組合，再由 Opus 用同一套標準重校三本的最終譯文：全 Sonnet 留下 28 處會影響理解的錯，全 Opus 4 處，Sonnet 讀＋Opus 翻 2 處。照定價換算 Sonnet US$37.7、Opus US$60.3、Sonnet 讀＋Opus 翻 US$38.9：Opus 貴在讀書（US$33），Sonnet 的翻譯也不便宜（初稿錯多，校稿後逐段重譯 189 次）。Sonnet 讀書時把一位女性角色取了男性的名字（定名）。另一個 repo 要另外安裝、版本要對齊、介面兩套（GUI 只在 ncte）。
- 決定：
  - 新增模型來源 `claude`（`NCTE_LLM_PROVIDER=claude`、網頁設定「Claude 方案」）：每個請求一次全新的 `claude -p`，步驟的提示詞取代 Claude Code 自己的系統提示，不帶工具、不讀使用者設定、不留對話紀錄（每次額外約 600 token）；每步的推理程度照 `stage_reasoning`（預設 medium，關係、覆核、校稿、修正檢查 high）以 `--effort` 傳過去。額度用完或連線失敗時等待後重試（最長每次一小時），不中斷。沒登入則立即停止。
  - 不收費：記錄的 `cost_usd` 為 0；CLI 回報的定價換算金額記在 `usage_json.list_cost_usd`，網頁顯示「Claude 方案・照定價約 US$X（不另收費）」，不顯示預算上限。
  - 預設模型：翻譯、定名與所有檢查用 Opus；切場景、讀場景、記憶整理、覆核、關係、角色印象、體例用 Sonnet（`stage_models`）。設定裡已選的 `claude/…` 模型保留；API 模型 id（OpenRouter 預設、審稿或備援模型）在這個來源沒有意義，換掉或移除。原本註解寫「讀書與翻譯用同一個模型」；程式只禁止換翻譯模型，讀書步驟本來就可以設，這次的整本實測顯示分開比較好，註解改正。
  - 把 ncte-agent 併回：任務佇列、背景引擎、`ncte agent start|next|submit|status|export|stop|resume`、`ncte mcp`（MCP 伺服器，選用套件 `pip install 'ncte[agent]'`）、`skills/ncte-translate`。來源名 `agent`；這種執行不能經 API 續譯（`ncte resume` 會要求改用 `ncte agent resume`）。ncte-agent 的 `drive` 由 `claude` 來源取代。
  - 預設來源改為 `claude`（沒有設定 `NCTE_LLM_PROVIDER` 時）；README 以 Claude 方案為主、OpenRouter 並列。OpenRouter 較快（一本約 3 小時對約 6 小時）、不占訂閱額度，留給沒有 Claude 訂閱的人。已在 `.env` 選了 openrouter／fal 的照舊。
- 不做：讓 agent 自己探索資料（開放工具讀全書）。理由：Sonnet 翻錯的段落，判斷所需的後文都已在輸入裡（模型沒用上，不是沒資料）；開工具每次重送累積的上下文（子代理每題約 4–5 萬 token）；自由搜尋會讀到後面才揭曉的身分與伏筆，繞過可見範圍。若要做，先做只能查 NCTE 紀錄、受可見範圍限制的「查筆記」工具，並先統計缺資料的錯有多少。
- 補充（2026-10-19，review 後的修正）：
  - 提示詞快取：Claude Code 把整段 `--system-prompt` 當一個快取區塊，只有逐字相同才讀快取；原本系統提示詞＝固定規則＋本批條件段（＋重試更正），schema 附在 user 訊息，smoke run 15 個請求只有 23% 讀快取，條件段不同的翻譯請求 0 命中。改為依 `cached_prefix_chars` 切開：`--system-prompt`＝該步驟固定的規則（含回答格式）＋該步驟的 JSON schema，每個請求逐字相同；本批條件段與重試的「重要更正」放進 user 訊息、在資料之前。OpenRouter 的 `cache_control` 做法不變（ADR-043）。回答格式只說一次（`translator.COMPACT_JSON`：只輸出一個 JSON 物件、不要說明與 code fence、寫成一行、代號照原樣），所有來源共用；原本 Claude 專用的 `ANSWER_RULE` 移除。線上結果（修正指示 5.1，範例書 smoke，4c13950）：31 個請求、照定價 US$1.13；cache read 占輸入從 23% 升到 38%（write 77% → 62%），每個步驟從第二個請求起都讀回整段 system prompt＋schema（translate 7 個請求裡後 6 個每次 3,489 token、scene_analyze 每場 7,404、memory_update 6,964），改前 translate 第 3 個請求 0 命中。38% 只因 smoke 每個步驟的請求少，整本時固定部分接近全命中。每個請求沒進快取的輸入只有 2 個 token：Claude Code 把 user 訊息也寫進快取（1.25 倍寫入），那部分每次都不同、不會被讀回，省不掉。之後（2026-10-19，整本實測後）schema 改由 Claude Code 的 `--json-schema` 傳（答案取回傳的 `structured_output`，沒有才用 `result`，程式的 Pydantic 驗證照跑），`--system-prompt` 只剩該步驟固定的規則；CLI 拒絕 schema 本身時立即停止（`FatalAPIError`，附原文），不退回把 schema 貼進提示詞。理由：整本實測 15 次沒過驗證的回答有 11 次是多了 schema 沒有的欄位。快取比例的變化尚未線上量。
  - 重試：Claude Code 拒絕指令本身（exit 2、stderr 有 unknown option／unknown argument／too many arguments）每次都一樣，立即停止並附 stderr，不再等最長約 4 小時；「沒登入」的字樣只在失敗（`is_error` 或 exit 非零）時檢查，模型的回答裡出現同樣的字不算。每次等待前寫一行原因到指令列或網頁的紀錄。
  - 模型分配（取代前文「預設模型」一條）：覆核與人物關係改用 Opus。這兩步整本只有幾個請求（範例那本 2–6 個），卻決定說話者、性別與人物關係，下游每一處你／妳與稱呼都靠它；用 Opus 的額外花費相對整本很小。現在 `CLAUDE_READ_STAGES` 是切場景、讀場景、記憶整理、角色印象、體例用 Sonnet；翻譯、定名、覆核、人物關係、規則確認、審稿、對照校稿、讀者檢查、修正驗收用 Opus。README 與網頁照程式改。效果尚未整本實測（ADR-062 的比較是覆核與關係在 Sonnet 時跑的）。

## ADR-063（2026-10-19）：校稿的「兩可」不算錯
- 背景：2026-10-19 review 檢視一本整本實測的對照校稿：回報為錯的 43 條裡，6 條其實是原文容得下兩種讀法（校稿偏好另一種）、3 條修正驗收判定原譯就對而保留原譯、1 條重譯後改壞。校稿提示詞已說「原文容得下目前的讀法、只是偏好另一種的，不算錯，不要回報」，但模型仍回報、而且只能報成 `meaning` 等錯誤類別，於是送去重譯：多花請求，也多一次改壞的機會。
- 決定：
  - 校稿的 `kind` 加 `ambiguity`：原文容得下目前的讀法、另一種讀法至少同樣自然、說不出「原文為什麼不能是目前的讀法」時歸這一類，`problem` 寫兩種讀法各自的根據，`fix` 寫另一種讀法的譯文。提示詞只寫這條通則，不舉特定句子（同一版 v1）。
  - 程式記成 `review:proofread_ambiguity`（severity low，掛在當時的譯文版本上），計入檢查點的 `ambiguities`；不加進重譯的 feedback、不重譯、不影響可驗收。網頁對照審稿頁把它列成「兩種讀法」供人看。哪一種讀法對由人或模型決定，程式不判斷（ADR-059）。
- 限制：模型可能把真的錯報成兩可（這時不會重譯）；效果要整本實測才知道，尚未量。

## ADR-064（2026-10-19）：後文線索——規則 4 的範圍、「讓前後的反應成立」、`read_through` 開關
- 背景：2026-10-19 的錯誤分析找到一類錯：判斷一句怎麼譯的線索就在同一個請求的下一兩段（不是防劇透擋掉的），模型沒用上——後一段旁白點出某人改了說法、後一句的反駁說明比較的是什麼、後一句的追問說明這句刻意沒說是誰、後一段解釋了一個詞，譯文都沒有反映。出錯的請求是整場翻譯（85–133 段）、Sonnet、推理 medium、平均每請求約 50 個思考 token；Opus 同流程少很多。診斷：模型照 `units` 順序從頭往後寫，寫這句時沒有任何東西要它先看下一段；提示詞裡「讓後面的反應說得通」只放在說話方式那條，而這類錯多半是內容不是說法；規則 4「不可把推測或後文資訊寫進譯文」沒界定「後文」，可能讓模型把「用後文理解」也當成禁區。
- 決定：
  - 規則 4 改措辭（同一版 v1）：後面的段落（同一批後面的 `units` 與 `context_after`）可以、也應該用來理解前面的句子；禁止的是把後面才揭曉或才說清楚的資訊提前寫進前面的譯文（增譯），以及把 `scene`／`memory` 的推測當成事實。懸念照舊保留。場景以外看得到多少由程式的可見範圍控制，不靠這條。
  - 「讓前後的反應成立」成為獨立的一節，放在判斷順序之後、翻譯規則之前：譯一句之前先看後面有沒有人反駁、追問、糾正、吐槽、模仿、評論或拿它對照；有的話，這句的譯法要讓那個反應讀得通（比較的是什麼、指的是誰或刻意不說是誰、語氣或說法的突然改變、一個詞後來被解釋成什麼），說法本身被吐槽或模仿時特徵要看得出來。這是在原文容許的讀法裡選一種，不是補資訊：後文說清楚的仍留在後文。原本規則 7 末尾「前後文有人吐槽、模仿或評論某句話的說法時…」併進這一節。只寫通則，不放分析裡的具體句子。
  - `translation.read_through`（預設關）：開啟時翻譯請求帶 `"read_through": true`，答案的 schema 是 `TranslationReadThroughOutput`——`read_through: list[str]` 排在 `translations` 前面（JSON 依欄位順序生成，模型得先掃完整批才填得出來），提示詞的條件區塊要求列出後面段落限制前面某句譯法的地方（被限制那句的代號加一句，最多 5 條，沒有就空陣列）。程式只把它存起來：該請求第一個留下的段落的 `translations.notes_json` 多幾條「通讀：…」（段落代號換回段落 id、人物代號換成名字），不判斷內容、不影響流程（ADR-059）；超過 5 條只留前 5 條。關掉時請求、schema 與提示詞和原本完全相同。agent 來源送出的答案依該任務的輸入選 schema。
- 為什麼開關預設關：每請求多約 100–200 個輸出 token；有沒有用、會不會讓模型把後文資訊提前寫進來，要等修正指示第 5.4 節的小樣本驗證（正例＋懸念、無線索、原本就對三種反例，V0–V3 四個變體）才知道。達標才改預設，並在本 ADR 補充結果。
- 不做（這次）：縮小場景批次或改回 1400 字（ADR-044 的理由仍在；若 5.4 顯示是注意力問題，先降 `scene_max_chars`）；翻譯推理改 high（額度上最貴，只在 `read_through` 不夠時試）。
- 限制：規則 4、新的一節與 `read_through` 的效果都還沒有線上驗證；改了 translate 提示詞，`prompt_version` 的雜湊跟著變。
- 補充（2026-10-19，修正指示 5.4 的小樣本驗證）：Sonnet 翻譯、四個場景整場重翻 725 段、V0–V3 每個變體兩次，Opus 只拿類別判（數字見 changelog「review 後的線上驗證」節）。正例 5 句裡真正重現錯誤的是 3 句（§59、§2353 在 Sonnet 上沒有重現）：V0 1/3、0/3；V1（規則 4＋新的一節）1/3、1/3，只穩定修好「不補出像誰」那句；V2（再開 `read_through`）1/3、1/3，清單明確列出另外兩句的限制、譯文照錯；V3（再加 translate high）3/3、2/3。懸念 12 句 8 次執行都沒有增譯；其他段落的改壞這個樣本判不出來（V0 自己兩次互比就有 3 段被判不同）。V3 輸出 token 約 V0 的 1.7–2 倍，照定價一次只多約 15%（快取）。統計力弱（3 句、各 2 次）。
  - 規則 4 的新措辭與「讓前後的反應成立」保留：沒有看到提前寫出後文資訊（懸念 0 增譯），且修好一句。
  - `read_through` 預設維持關：模型看到了沒用上，單開它沒有比 V1 好，還多輸出。
  - Sonnet 翻譯要推理 high 才用得上後文線索：只有 V3 修好了「看到了沒用上」的兩句。因此 Claude 方案、翻譯模型是 `claude/sonnet` 時，`stage_reasoning` 沒有設 `translate` 就用 high（`orchestrator.CLAUDE_SONNET_TRANSLATE`，在 `check_reasoning_effort` 套上，`--model claude/sonnet` 與設定檔的 `model: claude/sonnet` 都算）；Opus 翻譯不變（預設組合的翻譯就是 Opus，這次沒有證據要改）；使用者自己設的優先。代價照 V3：輸出約 1.7–2 倍、照定價一次約多 15%。

## ADR-065（2026-10-19）：平行化——校稿與讀者檢查的批次、跨章翻譯；讀場景合成一個請求的開關
- 背景：Claude 方案整本約 6 小時（OpenRouter 約 3 小時），大部分時間是一次一個請求在等：翻譯逐場景、校稿與讀者檢查逐批，每批還要等它自己的重譯與修正驗收。這些工作之間的依賴其實很少：校稿與讀者檢查的每一批在開始時就決定了要看的段落、譯文與前一批的結尾（程式在開始時一次切好），不需要等前一批的結果；記憶在翻譯之前已經讀完（ADR-023），一章的翻譯不靠另一章的譯文決定內容。
- 決定：
  - 併發數用既有的 `openrouter.max_concurrency`（預設 2，Claude 方案也用它：同時幾個 `claude -p`；agent 來源同時有幾個待答任務）；設 1 就和以前一樣一次一個。
  - 校稿、讀者檢查（4.1）：每一批（含它的重譯與修正驗收）交給一個 worker，和 `run_batches` 同一套做法（daemon thread、`done_q`、依序開始）。每批的統計各自累計，完成時在主執行緒加總；DB 寫入照舊在 `self.lock` 下。檢查點的 `done_until_ordinal` 只推進到「連續完成」的地方；越過缺口先完成的批次記在 `done_beyond`（段落 id），續跑時不再做，連續之後就移除。暫停（`_stop_reason`）或出錯後不再開始新的批次，已經開始的等它做完、結果照記（`FatalAPIError`、`BudgetExceededError` 等完之後拋出；其他例外也一樣等完再拋，不讓背景執行緒在拋出後繼續寫資料庫）。
  - 跨章翻譯（4.2）：場景依 `chapters` 分組，章與章之間併發、章內場景照順序；每個場景的規則確認與審稿在 worker 內做，`reload_glossary` 在 lock 下。一章失敗（致命錯誤、預算）時其他章做完當前場景就停。沒有章節資料時整本一組（和以前一樣）。交錯模式（`read_first: false`）不平行：它的記憶要跟著翻譯一場一場讀。
  - 讀場景合成一個請求（4.3）：`context.read_in_one_request`（預設關）。開啟時（只在 `read_first`），一個場景的分析與記憶整理用一個請求（`prompts/scene_read/v1.md`：兩份現有提示詞的規則逐字放在一起，只多了輸入與輸出的對應說明——第二部分的 `scene` 就是第一部分的答案、新人物用第一部分的 `temp_id`），答案是 `{"analysis": …, "memory": …}`；程式照原本的兩個 apply 函式處理：先寫分析，再把記憶答案裡的人物代號換成分析建立或對上的人物卡 id（`apply_scene_analysis(..., refs=)`，只是代號對照，不判斷誰是誰），再寫記憶。模型與推理程度沒有另外設定時跟 `scene_analyze`（Claude 方案是 Sonnet）。場景長到要分段讀、或這個請求失敗（被拒、答案不合格）時，那一場改回兩個請求。
- 已知取捨與差異：
  - 章首第一批看不到前一章剛翻好的譯文：前一章若還沒翻到結尾，`context_before` 只有原文、沒有 `translation`。單執行緒時它看得到。
  - 校稿與讀者檢查平行時，一批的重譯與修正驗收看到的前後段譯文（`context_before`、`around`）可能是鄰批改過或還沒改的版本，和一次一批時不一定相同；FakeLLM 下結果相同（測試），真的模型在批次交界的段落可能有差。發現的 id 與 `llm_requests` 的順序不同（集合相同）。
  - 讀者檢查在校稿之後才開始（它讀改過的中文），兩者之間不平行。
  - 合成請求：模型讀分析時沒有程式核對過的說話者（兩個請求時記憶整理看到的是核對後的 `scene`），也看不到分析新建人物卡的譯名；品質要 A/B（修正指示第 5.6 節）才知道，所以預設關。`--dry-run` 的估價仍以兩個請求計。
- 效果：平行化的實際時間與品質沒有線上量過（修正指示第 5.5 節，需額度）；離線測試只證明 FakeLLM 下併發 3 與併發 1 的發現、重譯、修正結果與譯文完全相同，以及中斷續跑不重做。

## ADR-066（2026-10-19）：校稿可以做兩輪以上（`context.proofread_passes`）
- 背景：整本實測（changelog「整本實測：新的 claude 來源」）裡，流程自己校稿抓 11 處；事後用同一份校稿提示詞、同一個模型（Opus）對最終譯文再校兩次（high、medium），各抓 6、8 處，和流程那一輪只重疊 1 處，兩次之間重疊 4 處。三輪合計 20 處不重複：單輪的召回大約一半，再跑一輪就多撈一批，比改提示詞直接。代價是一輪校稿的額度（那本照定價約 US$8，加上它的重譯與修正驗收）。
- 決定：
  - `context.proofread_passes`（1–3，預設 1）。第 k 輪（k≥2）在前一輪的重譯與修正驗收都做完之後開始，對整本現行譯文再校一次（不是只校前一輪改過的段落；範圍和第一輪相同：整本，或上次整本校完之後新翻的部分），發現照常交回翻譯並對照原文驗收；兩可的照常只記錄（ADR-063）。
  - 檢查點多記 `pass`（目前第幾輪）與 `passes`（做完的每一輪各自的統計）；`done_until_ordinal`、`done_beyond` 是目前這一輪的。一輪做完、下一輪開始前先寫好檢查點，所以在任何地方停下，續跑都從停下的那一輪、那一批接上，不重做前面的輪。job 的統計是各輪加總（`retranslated`、`issues` 等），`passes` 保留每一輪的；只設一輪時檢查點與統計和以前完全相同（沒有 `pass`、`passes`）。2.11 的 `upto_translation_id` 在最後一輪結束時記。
  - `ncte proofread --passes N` 覆寫設定。估價（`--dry-run`、網頁）的校稿字數乘上輪數。
- 為什麼預設維持 1：多一輪就多一份校稿的額度（以及它帶出的重譯與修正驗收），Claude 方案上是訂閱額度、OpenRouter 上是錢；要不要花由使用者決定。開法：設定檔 `context: {proofread_passes: 2}`，或對已翻好的書跑 `ncte proofread 書.epub --passes 2`。
- 限制：第二輪抓到的有多少是真錯、會不會把第一輪修好的又改回去，都還沒整本實測；數據只有一本書、三輪校稿。讀者檢查仍只一輪，在最後一輪校稿之後。網頁沒有這個設定的開關（照設定檔）。
- 補充（2026-10-20）：Claude 方案預設兩輪。`context.proofread_passes` 沒有設定時（預設值改為 null）由 `config.proofread_passes` 依來源決定：`claude` 是 2（`CLAUDE_PROOFREAD_PASSES`），OpenRouter、fal、本機與 agent 是 1；設定檔寫了（包括寫 1）或 `ncte proofread --passes N` 就照寫的。估價（`--dry-run`、網頁）用同一個函式，所以跟著乘。理由：整本實測三輪校稿（流程一輪、事後重校兩輪）彼此只重疊 5 處，第二輪平均多抓 6–8 處；Claude 方案多一輪的代價是訂閱額度不是錢，OpenRouter 上每一輪都要付費，維持 1。限制：第二輪抓到的有多少是真錯、會不會改回第一輪修好的，仍沒有整本實測；**下一次整本驗證若第二輪只多抓一兩處，就改回 1**。舊的工作區執行紀錄存的是當時的設定值（1），續跑不受影響。


## ADR-067（2026-10-19）：判錯的步驟和譯者用同一套原則；讀與譯已有的資料送到接收端
- 背景：整本實測（changelog「整本實測：新的 claude 來源」）三輪校稿（流程一輪、事後重校兩輪）抓到的錯幾乎不重疊；「原文省略主詞、中文照省略後讀者把動作接到別人身上」這一類，四輪只抓到一次。對照提示詞與程式：同一條原則只寫在譯者那一邊（譯者知道「不確定時保留省略」，校稿、修正驗收卻不知道「前後文已確定的主詞補上不算增譯」），審稿沒有判斷順序、沒有 tone／voice 類別、也沒有「兩可不算錯」；讀場景已經存下的資料（省略主詞的句子 `actions`、模型自己提的疑問 `uncertainties`、換場點的 `sure`、體例的 `honorifics_reason`）與譯者已經產出的旗標、`notes`，大多沒有送到判錯的步驟或網頁——譯者的 `subject_omitted_kept` 等旗標從來沒有人讀。
- 原則：
  1. 同一條原則寫在每個相關步驟，各寫它那個角色的一面：譯者「什麼時候補、什麼時候保留」，校稿「補錯或沒補是哪一類錯、補對的不是增譯」，修正驗收「補對的不是新資訊」。判斷順序（六條）翻譯、校稿、定名、體例、審稿、修正驗收共用，逐字相同。提示詞只寫通則，不寫個案，同一主版本 v1 內改。
  2. 資料送到，程式不判斷（ADR-059）：程式把讀的時候的判斷（附確定程度）、譯者的旗標與說明交給下一個看的模型或人；可以把旗標轉成待確認的項目、把人物 id 換成當時看得到的名字，但不判斷對錯。
- 決定：
  - 提示詞：譯者規則 3 補「省略會讓讀者接到別人身上時，用前後文已確定的人補上；不確定才保留並標 `subject_omitted_kept`」；校稿 `meaning`／`addition`、修正驗收 `new_error` 各寫對應的一面；修正驗收的 `new_error` 加褒貶與語氣；審稿與修正驗收加判斷順序；審稿加 `tone`、`voice`（定義與校稿相同，`issue_type` 枚舉加兩個值；medium 以上照常送修，修正驗收收到的是審稿者的說明與建議）、「兩可」的判準與 `other`；校稿 `speaker` 與讀者檢查 `voice`：對象或性別只是推測時，不分性別的「你」不算錯；記憶整理的 `category`、`form_type` 每個值一句說明；譯者的 `voice` 與體例的說話習慣牴觸時以本句原文為準。沒有程式載入的 `prompts/scenes`（ADR-036 的舊切法，ADR-059 拿掉）連同它的 task、schema、假回答一起刪除。
  - 接線：校稿每段、修正驗收每項多 `actions`（讀場景的省略主詞句：誰做的、對誰、確定程度，名字取場景結尾看得到的）；修正驗收的人物卡多 `voice`、`habits`（和校稿同一份）；送修正驗收的建議去掉給譯者看的樣板（`FIX_NOTE`）。
  - 譯者旗標：`subject_omitted_kept`、`speaker_uncertain`、`term_uncertain` 記成 `model_flag:…`（severity high），在該場景的規則確認（`confirm_flags`）和程式規則一起問；判假 `dismissed_by_check`，判真照規則確認的既有做法進審稿（標 `confirmed`，審稿沒報也會送修，修正照常對照原文驗收）。名單 `orchestrator.CONFIRM_MODEL_FLAGS` 和 `qa.rules.CONFIRM_RULES` 分開。`possible_source_error` 不變。`ruby_meaning_kept`、`wordplay` 與其他旗標在網頁對照審稿頁顯示。
  - 譯者的 `notes` 送到校稿（`translator_notes`）、審稿（items 的 `translator_notes`）與對照審稿頁；提示詞說明那是給審稿者的話、不是譯文。
  - 讀場景的 `uncertainties`：覆核多一種 `question`（附疑問、前後原文、場景人物）；回答（一句＋可選的 `character_id`）寫進該場景 `state_json` 的那一條（`answer`、`answer_reason`、`answer_character_id`），翻譯與審稿的 `scene.uncertainties` 帶上 `answer` 與 `answer_who`（只在那時看得到的名字）；回答過的不再問；故事頁顯示問題與回答。
  - `sure: false` 的換場點：故事頁與 `ncte scenes` 標「模型標需複核」與理由；不自動重切。
  - 體例的 `honorifics_reason` 存進系列體例（不送進翻譯請求），`ncte style` 與網頁譯名頁的小卡顯示；人改了敬稱方式就清掉模型的理由。
- 限制：效果都沒有線上量過（不跑額度）。譯者旗標轉成 high 之後，旗標多的書規則確認與審稿的請求會變多，而且在確認或審稿之前這些段落算「有未處理的嚴重發現」；簡單模式（非 context）沒有規則確認，旗標直接進審稿。回答疑問的品質、`actions` 對校稿召回的影響，要整本實測才知道。
- 補充（2026-10-20，第二批接線）：對照 `docs/architecture.md` 的資料流向表，把讀與譯已經存下、判錯步驟卻拿不到的資料再接一批。原則不變：程式只送資料、做字串比對、控制可見位置，不判斷意思；提示詞只加輸入說明（新欄位的說明是條件區塊，請求帶那個欄位時才出現，快取前綴不變；規則確認的兩條規則說明是固定文字，各補半句），v1 內改。
  - 定名：`names` 裡不是人名、有術語定義（`origin` 為 model／human）的項目附 `definition`；定名本來就看全書，定義取到全書為止（`memory/terms.definitions_shown`）。`context.term_definitions` 關閉時不附。說明：用來決定譯名，不是要寫進譯名。
  - 審稿：同一份場景 context 裡的 `memory`（上一章回顧、本章最近摘要、事實、物品；和翻譯同樣在場景開頭以前、同樣的名額與挑法）一起送，全空時不送；`scene.uncertainties`（含覆核的回答）原本就在。說明與翻譯一致：事實與摘要只用來理解前情，不可改變本句原文的意思、對象或方向。
  - 修正檢查：每批附本批原文出現的 `glossary` 與這些段落說話者的 `address_terms`，和校稿同一套挑法（抽成 `proofread.renderings`，校稿的 `notes` 也改用它）。說明：用來判名字與稱呼是否照既有譯法；稱呼隨場合、情緒調整語氣不算錯（與審稿的 `name_inconsistency` 同一說法）。
  - 校稿與修正檢查：每段附 `relation`——只有這段台詞的說話者與對象這幾對（最多 3 對，`repository.LINE_PAIRS`），在這一段已開始、還沒被取代的關係（`pair_relations(..., at=)`、`line_relations`），名字用場景結尾看得到的（和說話者標示相同），推測的標（推測）。說明：判敬語、你／您、稱呼輕重時參考，推測的不確定。
  - 規則確認：`possible_added_name` 的項目附本段與前後 5 段原文出現的人名譯名（`glossary_payload`，只留 category 為 character，可見到該段）；`second_person_gender` 的項目附這段台詞的對象與性別 `to`（名字與性別都取到該段為止，對象是推測的標（推測））。其他規則不附。兩條規則的說明各補半句。
  - 刻意不接：角色印象的個性 `personality` 與定位 `role`（可能含劇情——揭曉位置管得到引用的證據、管不到寫進去的內容——對逐句翻譯幫助小；只送口吻 `voice`）；讀者檢查仍只看中文（刻意模擬不懂日文的讀者）。
  - 限制：固定譯文的一次線上對照（兩邊各校稿兩輪，見 changelog）分不出差異，效果沒有量到；留著是因為補的是判斷依據的不對等，成本約一成。範例書（FakeLLM）上每個請求增加的字數見 changelog；長場景的審稿請求會多帶最多 20 筆事實（和翻譯同量）。修正檢查的稱呼取「最早那段以前用過的」，在本批第一次出現、又還沒定譯法的稱呼不給（和校稿、翻譯同一條規則）。


## ADR-068（2026-10-19）：本機模型當來源（`local`）；步驟模型依前綴分流
- 背景：使用者想評估長期改用本機模型。在 M4 Pro（64 GB）上實測四個模型（Qwen3.6-35B-A3B 4-bit、Gemma 4 26B-A4B QAT 4-bit、OpenSakura（Qwen3.6-35B-A3B 的輕小說 SFT）、Murasaki-4B），用翻譯階段的真實提示詞各跑兩段 50 段：速度 decode 39–73 tok/s、prefill 約 500–625 tok/s（整本約 5–8 小時，關思考）；沒有簡體漂移；意思準確但每 16 句有 1–2 個視角／說話者錯（Gemini 0）；妳／你在沒有讀取資料時是隨機的（Sonnet 修稿五次也一樣）。格式上：LM Studio 忽略 `chat_template_kwargs`，思考關不掉時一批 50 段想 8,000 token 都答不完；Qwen 4-bit 會把 JSON 字串收尾的 `"` 寫成 `」`（50 段壞 34–37 段），加一句回答規則後歸零；Gemma 的 JSON 結構會滑掉（每項多一個 `]`、key 寫錯），需要 grammar。
- 決定：
  - 新增來源 `local`（`NCTE_LLM_PROVIDER=local`、網頁「本機模型」）：任何 OpenAI 相容的本機伺服器（LM Studio、llama-server、mlx_lm.server），位址 `local_base_url`（預設 LM Studio 的 1234），模型 id `local/<伺服器的 id>`，`local/default` 是伺服器已載入的那個。價格 0、沒有 /generation、timeout 1800 秒、不需金鑰。
  - 思考由模板控制：找得到模型的 `chat_template.jinja`（LM Studio 的模型資料夾；GGUF 從檔頭讀）就自己套模板、送 `/completions`，`enable_thinking` 只在步驟設了推理程度時為真（`stage_reasoning`），`response_format` 的 grammar 照用；找不到模板就退回 `/chat/completions` 並記一條提醒。預設不設推理程度。
  - 回答方式與其他來源相同（每步的說明裡的 `COMPACT_JSON`）；本機只多附一句 JSON 語法提醒：字串值的界定符號是 `"` 不是 `」`。這是輸出格式的通則，不是針對某本書的規則。真流程發現寫成「字串以 ASCII 雙引號開頭與結尾」會被當成內容規則（10 段譯文以 `"` 開頭），所以改成只說界定符號。
  - `json_object` 模式本機伺服器不收：不送 `response_format`，記為 `prompt_only`，照舊由 Pydantic 驗證。
  - 步驟模型依前綴分流：`claude/…` 與 `local/…` 各自有來源，`stage_models`、`review_model`、`fallback_models` 可以指到另一個來源（讀取在本機、翻譯在 Claude 方案，或反過來）；執行的來源仍是主來源（紀錄與各來源專屬的路徑看的是它）。`claude` 來源不再丟掉 `local/…` 的步驟模型。
- 不做：兩段式（OpenSakura 初稿 → 另一個模型改寫）。實測改寫模型會錨定在草稿上：Gemma 50 行只改 12 行、該改的一個不改；Sonnet 肯改（42–47 行）但妳／你仍隨機，且用量與自己翻相同。要用 OpenSakura 的準確度，位置是第二意見（兩個譯本意思不一致的段落送 fix_check），不是初稿。
- 結果（2026-10-20，真流程序章＋第一章 1,026 段，Qwen3.6-35B-A3B 4-bit 全本機）：3 小時 29 分、389 個請求、零失敗收尾，但對照正式版你／妳相反 35 句（Gemini 同一章 1 句）；有讀取資料也幾乎不寫「妳」。所以本機模型不當主力：預設來源不變，`local` 留作實驗與混合跑（讀取、校稿在 Claude 方案，翻譯在本機）。
- 未定：哪個本機模型能扛翻譯階段。候選是 dense 模型（Gemma 4 31B、Qwen3.8-27B）只做翻譯、或補 grammar 後端給 Gemma；回答規則那句已改寫，效果要下一次本機跑才知道。


## ADR-069（2026-10-20）：術語的意思（`terms` 步驟）；事實與稱呼的名額跟著批次大小
- 背景：一本奇幻戀愛輕小說整本實測時，§1749「最初の頃は魔法じゃなくて戦力外の魔術士として扱われてた」被翻譯、校稿、修正驗收一路讀成「一開始用的不是魔法」。讀的階段其實記下了定義這兩個詞的事實（§23 賢者將魔術昇華為魔法、§614 那個國家原本有魔術但難以用於戰鬥、§617 魔力迴路取代魔術所需的道具與詠唱），但那個翻譯請求（一個場景 123 段）只拿到 2 筆無關的事實：`select_facts` 只有 `max_retrieved_evidence`（預設 5）個名額，用整批文字和事實證據句的字面重疊打分；§614 那筆的證據句是段落開頭的一句，根本不含「魔術」二字。譯名表裡只有「魔術→魔術」，沒有任何解釋。
- 原則（ADR-059）：模型讀、判斷意思；程式只做字串比對（詞在不在這段原文、在不在事實的字串裡）、核對答案引用的代號確實是給過的證據、控制可見位置。程式不判斷一個詞是什麼意思、哪些詞是一組。
- 決定：
  1. 事實名額跟批次走：`memory_context` 把 `max_retrieved_evidence` 當作每 25 段的名額（`retrieval.batch_quota`：段數除以 25 無條件進位，至少原值、最多 4 倍；123 段的場景拿 20 筆），記憶區塊的字數預算同比例放寬、上限 8,000 字（`memory_chars`）。挑選方式不變（同樣的打分、同樣的順序），只改留下幾筆。
  2. 稱呼的名額同樣跟批次走：`address.context_items` 原本固定留 12 個（本批用到的稱呼，用得多的優先），翻譯與校稿改為每 25 段 12 個、最多 4 倍。人物卡、道具、說話者、省略主詞的句子本來就沒有名額上限；前情摘要依故事位置挑（本章最近 4 段＋上一章 1,200 字），不是依字面，不變。
  3. 記憶整理規則 1 補一句通則：`evidence_quote` 要選直接寫出這筆事實、含主體與關鍵詞的那一句，不要選只是同段開頭的句子（`memory_update`、`scene_read` 兩份，逐字相同）。
  4. 新步驟 `terms`（術語的意思），在體例（house_style）之後、定名（naming）之前：
     - 位置：它要整本讀完（例句分散全書、事實要齊）與記憶整理留下的譯名表候選，用不到人物關係與角色印象；放在定名之前，是因為定名在 `naming: review` 時會停下來等人，術語先做完不會被擋在暫停後面。定名之後譯名可能改：請求裡的 `zh` 是送出時從譯名表查的，不存在定義裡，所以跟著改。
     - 輸入（程式的字串比對）：譯名表裡 category 為 term／skill／item／organization／place（不含人名）、在本書正文（text 與 heading）出現兩次以上的詞，依次數取前 60 個，人工定義過的不問；每個附最多 3 句含這個詞的原文例句（分散全書；取詞所在的那一句，太長就截在詞的前後）、最多 5 筆 `predicate`／`object`／`evidence_quote` 字串含這個詞的事實（分散全書；推測的標 `guess`、時期附 `period`），都附位置。每個請求 20 個詞，代號在整個步驟裡唯一（`t` 詞、`s` 例句、`f` 事實）。
     - 回答：`definition`（一兩句繁中：在這本書裡是什麼、和相近的詞差在哪；只寫原文寫明的）、`evidence`（例句或事實的代號，至少一個）、`revealed_from`、可選的 `contrast_with`。程式核對：`evidence` 不能是空的，**每個代號都必須是這次給過的**，否則整筆不收（計入 `rejected`）；定義空白不收。可見位置＝引用的證據與 `revealed_from` 裡最晚的位置（`revealed_ordinal`），之前的請求不會看到它；`revealed_from` 不是給過的代號時用最早的證據。
     - 被內容過濾擋下：照 `call_in_parts` 切半，最小到一個詞；擋下的詞記 `terms_blocked`，它原本的定義不刪。
     - 儲存：新表 `term_definitions`（migration 31，只加不刪）：定義、`contrast_with`、證據（種類與位置）、`since_ordinal`、`revealed_ordinal`、`origin`（model／human）、run。再問一次時，被問到的詞的模型定義換成新答案（沒回答的就沒有定義）；人工的（`ncte glossary define`）從書的開頭就可見，永遠不被模型覆蓋，也不再問。
     - 送到哪裡：翻譯（含修正重譯）、審稿、對照校稿、修正驗收的請求，凡是本批原文出現某個有定義的詞、而定義在這個位置已可見，就附 `term_definitions: [{ja, zh, definition}]`（`match_text` 字串比對，和譯名表的附法一樣；翻譯看本批與前後文、可見位置看本批最後一段，校稿看整段、可見位置看段末，修正驗收逐段看各段自己的位置）。四份提示詞各加一行輸入說明（條件區塊，只在請求帶這個欄位時出現，快取前綴不變）：這是讀完全書後整理的術語意思，用來理解原文裡這個詞指什麼，不是要寫進譯文的內容。
     - 提示詞 `prompts/terms/v1.md` 只寫通則：只寫原文寫明或明確表現的意思、不用外部知識、不劇透（後面才寫出的意思就引用後面的證據並把 `revealed_from` 設在那裡）、相近詞要寫出差別（原文沒寫清楚的差別不要自己定）、推測與角色認知不是設定、不建議改譯名、材料不夠的詞不要回答。沒有任何書裡的例子。
     - 模型：Claude 方案下用翻譯的模型 Opus（定義錯了會影響全書，而整本只有 1–3 個請求）；`CLAUDE_READ_STAGES` 不含它。
     - 開關：`context.term_definitions`（預設開）。關閉時不建 job、不發請求、也不送任何定義（包括人工寫的），方便 A/B。
     - 估價：`PER_RUN_STAGES` 加 `terms`，沒有紀錄時 sample share 0.01（和體例同級，是依大小猜的，不是量的）。網頁進度多一個「術語」階段；譯名頁下方一張「術語的意思」小卡（唯讀）。指令：`ncte names terms`（已讀過的書只跑這一步）、`ncte glossary define 書 詞 "意思"`（人工定義；不給意思就列出；`--drop` 刪除）。
- 代價：每本書多 1–3 個 Opus 請求（60 個詞時輸入估計 5–8 萬字、輸出約 60 段短說明；依每詞 3 句例句與 5 筆事實的長度推算，沒有量過），以及長場景的翻譯請求多帶最多 15 筆事實（約多 3–5 千字）、校稿與修正驗收多帶幾段定義。都還沒有量。
- 限制：
  - 沒有線上跑過：定義的品質、會不會把後期才揭露的意思寫進早期可見的定義（程式只能保證「不早於引用的證據」，管不到模型把引用之外的東西寫進去）、對 §1749 這類錯的效果，都要整本實測。
  - 字串比對會把包含關係也算進去（詞 A 是詞 B 的一部分時，B 出現的段落也算 A 出現、也附 A 的定義）；這是比對，不是判斷，定義本身要寫出差別。
  - 只看譯名表裡的詞：記憶整理沒有收進譯名表的術語不會被定義；人名（character）不在範圍內。
  - 章節標題與目錄的翻譯請求不帶記憶，也不帶定義；讀者檢查（只讀中文）與規則確認不帶。
  - 網頁不能編輯定義（只能用指令）。


## ADR-070（2026-10-20）：附屬的成分不拆成獨立的斷言；判意思之前先列原文容許的讀法
- 背景：一本奇幻戀愛輕小說整本實測時，一句台詞的主幹是「她被當成什麼」，前面帶一個對比的成分（「不是被當成 A，而是被當成 B」）。譯者把對比的那一半拆成一句獨立的陳述，等於替她斷定了當時的一種狀態；校稿抓到後改成另一個獨立陳述，又替她斷定了相反的狀態；修正驗收看出兩邊各有道理，卻判成「修正改出新錯」退回。官方譯本只寫主幹，不碰那一半的斷定。兩個問題：(1) 譯者把一句裡附屬的成分譯成另一個獨立斷言；(2) 判斷的人沒有先把原文容許的讀法攤開，看出每種讀法寫成中文都多斷定了什麼。
- 決定（提示詞只寫通則，不寫書裡的句子或詞、不列文法清單；同一主版本 v1）：
  1. 翻譯規則 5 加一個子項：原文一句話裡附屬於主幹的成分（對比、修飾、條件、讓步）留在附屬的位置，不拆成另一句獨立的斷言；拆開時容易替原文多說一件它沒說的事（誰做了什麼、當時是什麼狀態）。中文需要拆句時，拆出來的部分只說原文那個成分本身說的。
  2. 校稿 `meaning`：判斷之前先列出原文的文法與前後文容許的讀法；譯文落在其中一種就不是 `meaning`（另一種同樣自然時歸 `ambiguity`）；每一種讀法寫成中文都比原文多斷定了什麼、而譯文也寫了時歸 `addition`，`fix` 寫不帶這些斷定的寫法；`problem` 寫出列出的讀法。`ambiguity` 補一句：兩種讀法都多斷定時照 `meaning` 那條處理。
  3. 修正驗收：寫 `gist` 之後，原文容許兩種以上讀法時在 `reason` 列出；`before`、`after` 各落在不同讀法、都說得通 → `issue_invalid`（保留 `before`）；兩者都多斷定 → `undecided`，`reason` 寫不帶斷定的寫法。`new_error` 只寫原文容許的任何一種讀法都沒有的錯。
  4. 審稿 `mistranslation`：同樣先列讀法；都多斷定時報 `addition`，`suggestion` 寫不帶斷定的寫法；`evidence` 寫出列出的讀法。
- 「先列讀法」只放在判意思的步驟（校稿、審稿、修正驗收），不放進翻譯：翻譯每一句都列讀法，輸出與思考會隨全書句數成長；判錯的步驟只在它要下判斷的句子上做，量小得多。翻譯那邊只用規則 5 的子項防止拆出斷言。
- 不加 schema：修正驗收的讀法寫在 `reason`（`FixCheck` 不變），程式不判斷（ADR-059）。
- 限制：沒有線上量過（不跑額度）。校稿與審稿在「每種讀法都多斷定」時歸 `addition` 會送去重譯，若模型把一般的兩可也說成多斷定，重譯會變多；修正驗收判 `undecided` 的會留著待看。列讀法讓 `problem`／`evidence`／`reason` 變長，輸出多少沒有量。

## ADR-071（2026-10-20）：ChatGPT 方案當模型（`codex` 來源）
- 背景：使用者也有 ChatGPT 訂閱，想讓它的額度也能翻書（或只做某一步），不經 OpenRouter 付費。OpenAI 的 Codex CLI 有非互動模式 `codex exec`，用使用者自己的 ChatGPT 登入。
- 實測（codex-cli 0.162.1，2026-10-20，手動跑，不是整本）：
  - `--output-schema <檔>` 有效：`-o <檔>` 寫出的最後訊息是符合 schema 的 JSON 字串。`--json` 在 stdout 輸出 JSONL 事件：`thread.started`（`thread_id`）、`turn.started`、`item.completed`、`turn.completed`（`usage`：`input_tokens`、`cached_input_tokens`、`cache_write_input_tokens`、`output_tokens`、`reasoning_output_tokens`）。
  - 固定負擔：Codex 每個請求帶自己的系統提示與工具說明，一句話的請求輸入約 23,000 token。用 `-c model_instructions_file=…` 換掉它的基礎指示、並把 `codex features list` 裡所有 enabled 的功能都 `--disable`，降到約 10,400 token；兩次連續呼叫都沒有讀到快取（`cached_input_tokens` 0）。比 Claude 方案每次約 600 token 的額外負擔大得多，而且固定負擔不會因快取變便宜。
  - 帳號可用的模型在 `~/.codex/models_cache.json`（gpt-6.1-sol、gpt-6-sol、gpt-6-astra、gpt-6-luna、gpt-5.6-sol／terra／luna），推理程度 low…max（部分有 ultra）。
- 決定：
  - 新增來源 `codex`（`NCTE_LLM_PROVIDER=codex`、網頁「Codex（ChatGPT 方案）」），`llm/codex_cli.CodexCLIClient` 照 `claude_cli` 的結構：每個請求一次 `codex exec --skip-git-repo-check --ignore-user-config --ignore-rules -s read-only … --output-schema … --json -o … -m <model> -`，在每個請求自己的空暫存目錄執行，用完刪除。步驟的固定規則（`cached_prefix_chars` 之前）寫進 instructions 檔；本批條件段與重試更正放 stdin 開頭，再接資料（同 ADR-062 補充的切法）。推理程度照 `stage_reasoning` 以 `-c model_reasoning_effort=…` 傳，模型不接受的程度不傳。
  - 要關的功能在第一個請求前問一次 `codex features list`（每行「名稱 階段 true/false」，取 true 且階段不是 removed 的）；問不到就不帶 `--disable`，記一行。
  - 不收費：`cost_usd` 0；Codex 不回報價格，`usage.list_cost_usd` 也是 0（沒有定價可換算），token 數照記。網頁金額欄顯示「Codex 方案（不另收費）」，不顯示預算。
  - 方案額度：使用者要每本書記錄用了多少方案額度。實測不加 `--ephemeral` 時，Codex 每次請求後在 `~/.codex/sessions/YYYY/MM/DD/rollout-*-<thread_id>.jsonl` 寫入 `rate_limits`（`primary`／`secondary`：`used_percent`、`window_minutes`、`resets_at`）。所以不帶 `--ephemeral`；從 `thread.started` 取 `thread_id`，讀那個 rollout 檔最後一筆 `rate_limits`，存成 `usage["plan"] = {"windows": {"weekly"（10080 分鐘；1440 是 daily，整小時寫成 "5h"）: {"used": 0–1, "resets_at": epoch}}, "source": "codex"}`，讀完刪掉這個 thread 的 rollout 檔（失敗的嘗試也刪）。讀不到就不填，不影響請求。Claude 方案之後用同一格式。
  - 預設模型 `codex/gpt-6.1-sol`（所有步驟）；`codex` 來源只留 `codex/` 的步驟模型、審稿與備援模型，不帶 temperature，推理程度預設 medium；覆核、人物關係、修正驗收、校稿照 `DEFAULT_STAGE_REASONING` 是 high；校稿輪數預設 2（同 Claude 方案：一輪花的是額度，不是錢）。
  - 前綴分流加 `codex/`：Claude 方案的 run 可以用 `stage_models: {proofread: codex/gpt-6.1-sol}` 把某一步交給 Codex。**Claude 方案的預設不變**，Codex 只在使用者設定時用。順帶修正：原本 Claude 方案只要 `stage_models` 有任何其他來源的模型，讀書步驟就不再預設 Sonnet（整個變 Opus）；改為只補沒設的讀書步驟，一步交給別的來源不影響其他步驟的預設（本機來源同樣適用）。
  - 失敗：exit code 非 0、沒有 `turn.completed`、或有 `type` 含 error／failed 的事件都算失敗。等待與 Claude 方案相同（額度類固定間隔、其他走梯子）；未登入（失敗時的訊息含 login、not logged in、unauthorized、401）立即停止；命令列被拒（exit 2、stderr 含 unexpected argument、unknown option／feature／variant 等）立即停止。
- 限制：rollout 檔的事件結構只看過 `rate_limits` 那一段，程式在每一行 JSON 裡找最後一個 `rate_limits` 物件，不依賴外層鍵名。失敗時的事件與 stderr 格式沒有實測過，額度用完的字樣是猜的（凡是失敗都會等待重試，只是額度類若沒認出會走梯子、約四小時後放棄）。沒有整本實測：品質、速度、額度夠不夠翻一本都未知。`output_tokens` 是否已含 `reasoning_output_tokens` 沒有核對（兩個都記）。

### ADR-071 補充（2026-10-20）：不用 `--output-schema`；關掉 skills 說明；失敗嘗試的 token 也記
- 實測：範例書第一次真的跑（gpt-6.1-sol），42 個請求有幾個各卡約 30 分鐘：模型輸出一直寫到 128,000 token 的輸出上限（`Incomplete response returned, reason: max_output_tokens`），重試後才過；過了的譯文句尾也有亂碼（「…少女。W取」「第二章　在山丘上全球 end?」）。拿卡住那次的同一份提示各跑 4 次：帶 `--output-schema`（OpenAI 的嚴格格式）時，gpt-6.1-sol medium、high、不換基礎指示、gpt-6-sol 都會在譯文字串結尾冒出亂碼或接著無限輸出空白，約一半的嘗試出事；只留兩個必填欄位（沒有後面的選填欄位）、或完全不帶 `--output-schema` 時，4 次都正常。看起來是受限解碼在「譯文字串結束後還必須寫下一個欄位」時把模型擠歪；`reasoning_output_tokens` 在這些請求都是 0。
- 決定：
  - 不帶 `--output-schema`；步驟的 JSON schema 寫在固定規則（instructions 檔）的最後一段「回答格式」，回答照所有來源一樣由 NCTE 自己驗證（Pydantic、單元 id 檢查、重試更正）。上一版的嚴格格式轉換（`to_openai_strict`／`from_openai_answer`）與 schema 被拒立即停止的判斷一起移除。
  - 加 `-c skills.include_instructions=false`：Codex 會把 skills 的使用說明（約 15,000 字元）放進每個請求，`--disable` 關不掉；這個設定每個請求少約 3,200 token。
  - 失敗的嘗試（輸出上限、逾時）也耗方案額度：從那個 thread 的 rollout 檔讀最後一筆 `total_token_usage`（逾時的從被停下前已印出的 `thread.started` 取 thread id），加進這個請求的 token 數，另存 `usage["failed_tries"]`。rollout 檔一樣讀完刪除。
- 修正後重跑範例書：34 個請求全部一次成功，約 7 分鐘（修正前同一本約 1.5 小時，大多卡在那幾個請求），譯文沒有亂碼；每個請求的輸入 8,400（術語）到 13,200 token（讀場景），切場景的請求從約 12,100 降到 9,000。每週額度讀數 2% → 3%。
- 限制：只跑過範例書；整本的品質、速度與額度未知。固定負擔仍約 8,000 token／請求（Claude 方案約 1,100）；快取只偶爾讀到。

## ADR-072（2026-10-20）：每本書用了多少方案額度
- 背景：使用者要「每本書用了多少額度，Claude -p 還是 codex 都要記錄」，而且每個人的方案不同，不能只記 token 或照定價換算的金額。
- 實測：`claude -p --output-format stream-json --verbose` 的事件裡有 `rate_limit_event`，`rate_limit_info.unifiedWindows` 給每個時間窗的已用比例（`five_hour`、`seven_day`：`utilization` 0–1、`resetsAt`）；`--output-format json` 沒有這一項。Codex 的見 ADR-071（rollout 檔的 `rate_limits`）。同一天 Codex 的每週額度中途重置過一次（20% → 1%，`resets_at` 往後移）。另外：`claude -p` 在專案資料夾裡執行時會讀那裡（與上層）的 CLAUDE.md，即使 `--setting-sources ""`：同一個請求在專案裡輸入多約 1,300 token，模型還知道專案名稱；`--bare` 會跳過，但只接受 API 金鑰、不能用方案登入。
- 決定：
  - `claude_cli` 改用 `stream-json --verbose`，取 `type: result` 的事件當回答（與原本的 JSON 同欄位），最後一個 `rate_limit_event` 存成 `usage["plan"]`，格式同 Codex：`{"windows": {"5h": {"used", "resets_at"}, "weekly": {…}}, "source": "claude"}`（`five_hour` → `5h`、`seven_day` → `weekly`，其他名稱照原樣）。讀不到就不填，請求照常。
  - 每次 `claude -p` 在自己的空暫存目錄執行（同 Codex），不讀任何專案的 CLAUDE.md；使用者自己的 `~/.claude/CLAUDE.md` 仍會被讀（沒有不需 API 金鑰的關法）。
    - 更正（2026-10-23，Claude Code 2.1.309）：加了 `--system-prompt` 之後，使用者自己的 `~/.claude/CLAUDE.md` 也不會帶進去。同一個請求加不加 `--safe-mode`（不載入 CLAUDE.md、可用方案登入）輸入都是 626 token，問模型有沒有收到那份檔案裡的指示也答沒有。所以不需要 `--safe-mode`。
  - `reports/cost_report.plan_usage`：依來源（`usage["plan"].source`，或 provider 是 claude／codex）彙總 token（輸入、快取讀寫、輸出、推理、失敗嘗試）與每個時間窗的已用比例：依完成時間排序，`resets_at` 相差 120 秒內算同一個窗；第一個窗算「最大 − 最小」，之後每個窗（中途重置）算「最大 − 0」。結果在 `cost_report` 的 `plan_usage`、`ncte report` 的一行、網頁總覽的「用掉的方案額度」卡。
  - 顯示的是使用者自己方案的百分比，不換算成絕對量或金額。
- 限制：比例是整個帳號的，同一時段其他用量（別的對話、別的工具）會一起算；第一個請求自己用的量算不到（每個請求結束後才讀）；Claude 的 `utilization` 只到小數兩位（1%），Codex 的 `used_percent` 是整數百分比，短的執行讀數可能是 0。

## ADR-073（2026-10-20）：術語補漏：讀書沒列入譯名表的術語由模型從事實與摘要補上
- 背景：術語定義（ADR-069）只問譯名表裡的詞。拿 gemini-3.8-flash 讀過的奇幻愛情那本抽查時，譯名表沒有「魔術」，§1749「魔法じゃなくて戦力外の魔術士として扱われてた」三個模型都可能讀錯（Codex 翻與校都寫成「不是被當成魔法」）；換成 Claude 讀過、有「魔術」定義的副本，Codex 與 Claude 重翻都對。讀書的模型漏記一個設定用語，後面翻譯、校稿就永遠拿不到它的意思（ADR-069 的限制「不在譯名表裡的術語不會被定義」）。
- 決定：
  - 術語這一步先多問一個請求（`analysis/terms.candidate_request`，提示詞 `terms_candidates`，同一步的模型）：給全書的事實（最多 400 筆，分散全書；主詞、述語、受詞與原文依據）、各章摘要、已知的詞（譯名表全部的原文，含人名，與人工定義過的詞），請模型列出這本書有自己意思、或和另一個詞成對區分、但還沒列入的術語，每個附依據的代碼。
  - 程式只檢查（`take_candidates`）：引用的代碼是給過的（至少一個）、不在已知裡、在正文出現至少 2 次；最多收 20 個。是不是術語由模型判斷（ADR-059）。收下的詞和譯名表的詞一起走原本的定義請求（`zh` 空，表示還沒有譯名），證據檢查與顯示位置照 ADR-069。
  - 設定 `context.term_candidates`（預設開）；請求失敗只記一筆 `terms_failed`，譯名表的詞照樣定義。
- 實測（2026-10-20，抽查，不是整本；舊的 Gemini 工作區副本，只補跑術語這一步再重翻、校一輪）：
  - 奇幻愛情：Claude 補 16 個詞、Codex 8 個、Gemini 5 個，三者都補上並定義了「魔術」（寫出它是「魔法」出現以前的舊技術、使用者叫「魔術士」）。§1749 三者重翻都對（補之前 Codex 錯）。
  - 四本書（奇幻愛情、校園日常兩集、另一本無官方版的輕小說），每本隨機 4 場共 733 段，Claude、Codex、Gemini 各在自己的副本上補術語、重翻、校一輪；盲評（Opus，每段四個版本隨機標號：舊的 Gemini 整本譯文與三個新版本）大錯／小錯：舊 Gemini 4／28、Gemini 2／33、Claude 0／9、Codex 0／5。大錯都是舊 Gemini 或 Gemini 的：「代わりに」譯反、「背靠背」（原文是靠在對方身前）、性別沒記錄的角色被稱「妳」（Claude、Codex 用「你」）。
  - 用量：Claude 60 個請求、約 10 分鐘；Codex 72 個、約 16 分鐘，每週額度 5% → 7%；Gemini 68 個、約 11 分鐘、US$1.21。Claude 的 5 小時額度讀數同時含這個對話與評審，不能當這次的用量。
- 限制：評審是 Claude（Opus），可能偏好 Claude 的譯法；樣本 733 段；舊 Gemini 譯文走的是 10/16 的整本流程（含兩次以上審稿），新版本只有翻譯、場景審稿與一輪校稿，兩者流程不同。補漏請求的輸入隨事實數增加（這本 155 筆，上限 400 筆）。

## ADR-074（2026-10-20）：翻譯與判斷的三條通則、提示詞整理、依翻譯實務修訂、對照校稿兼做潤稿
- 背景：四本書 733 段的盲評（ADR-073）裡，錯誤集中在五類：照搬日文漢字（遊技場、軽薄、大味）、自己加料（「無數」「鐵鏽般」「只有」）、決定句子邏輯的小詞漏掉或讀錯（だけ、代わりに、それなのに、と思う、も 的範圍）、句子不通、性別與指稱；第三類三個模型都會犯。另外沒有任何一步做潤稿：校稿只回報錯誤，審稿與讀者檢查只在嚴重時提不自然，修正驗收見原譯意思說得通就保留原譯。
- 決定：
  - 三條通則寫進判斷順序（翻譯、審稿、對照校稿、修正驗收、定名、體例共用、逐字相同）與各步驟的錯誤類別：決定句子邏輯的小詞「作用與範圍要保留，手段不限、不必逐詞對應」；日文漢字詞在臺灣中文意思不同時不照搬；「潤飾只改怎麼說，不改說了什麼」——判準是讀原文的人從這句與前後文得不出的就是多加的（數量與範圍、確定程度、新的事實、畫面或比喻、動作或人物、評價或程度），中文文法需要的成分、前後文已確定的事、為傳達原文效果（說話方式、雙關、笑點、慣用語）而改寫的補償不算。
  - 全面檢查提示詞（49 項）後處理互相矛盾與說法走樣：說話對象或性別只是推測時用「你」在五個步驟一致；前後文已確定的主詞補上不算增譯（審稿原本沒有這個例外）；審稿只認 `verified: true` 的譯名；貶稱的判斷看中文讀者怎麼讀，刪掉兩個寫錯的例子；同一條「不要加料」在翻譯提示詞講了八次，合成一條；單一案例的規則改寫成通則；審稿 `voice` 的改寫欄位名改正為 `suggestion`。
  - 依翻譯實務修訂（Codex gpt-6.1-sol high 與 Opus 各自審查後合併）：拆長修飾語是常態（拆時不得把條件、讓步寫成確定的事）；名字加敬稱不是暱稱；片假名外文名用臺灣通行譯名、新字體改正體字；親屬詞或職稱拿來叫沒有這層關係的人時，讀書不配給已知角色、翻譯用同樣當一般稱呼的說法；日本特有事物有通行說法用通行說法、沒有就保留；口頭禪是表現方向，不必每句譯出；原文本身在辱罵時保留程度；讀者檢查只依讀到這裡已交代的內容；敬稱依種類分別定規則（體例規則上限 6 → 10）；原文省略第二人稱時，中文需要才補，前提是前後文確定對誰說，照那人的性別寫，同一人前文用過「妳」也是依據（仍逐句判斷，不做成體例）；措辭改成臺灣中文的自然說法（上下文→前後文、主語→主詞、劇透→爆雷、「上下文不支持」→「前後文看不出來」等）。
  - 對照校稿兼做潤稿：新類別 `expression`——意思沒錯，但中文讀起來有具體障礙（語序照搬日文、修飾語太長、拖沓、台詞不像這個人說的話、語域不合、指涉讀不懂）；`fix` 要意思、視角、語氣、口吻都不變、不增不減。送修時給譯者另一段說明；修正驗收對它另有判準（意思不變且障礙解決＝`fixed`；其實讀得順＝`issue_invalid`；改了意思寫進 `new_error`）。同一次執行裡已因 `expression` 改過的段落，後一輪不再潤。
  - 不改：兩種讀法都說得通就不算錯的判準（防止憑偏好換稿）；你／妳不做成體例；譯名異議與術語分階段等需要改資料結構的項目另做（todo）。
- 實測（抽查，Claude 方案，四本書 733 段）：
  - 對照校稿 A/B（同一份 Gemini 舊譯，校一輪）：有改動的 15 段，大錯／小錯 校前 5／9、舊提示詞 2／3、新提示詞 0／1；新提示詞多抓到漢字照搬、詞義錯、多加程度、兩處性別不明卻稱「妳」，沒有把對的改壞。
  - 翻譯 A/B（三個模型各用新舊提示詞重翻 680 段，同表盲評）：Claude 小錯 10 → 4（另有 1 處大錯：原文沒有第二人稱卻補了「你」，對象是女性）、Codex 16 → 19、Gemini 45 → 46，差別在雜訊內：這些規則翻譯時顧不到，要靠校稿這一關。
  - 潤稿：Claude 譯文校兩輪，只因潤稿而改的 10 段流暢度（1–3）1.3 → 2.7、小錯 3 → 0；Gemini 舊譯校一輪，只因潤稿而改的 20 段 1.55 → 2.65、小錯 5 → 1（1 處潤稿多加了「全數」）；沒有段落被潤兩次。
- 限制：評審是 Claude（Opus）；潤稿會增加重譯與驗收的請求（Gemini 舊譯一輪從 14 處升到 56 處，Claude 譯文兩輪 21 處）；樣本小，整本的額度影響未量。

## ADR-075（2026-10-20）：術語定義分階段揭露
- 背景：術語定義（ADR-069）從它引用的最晚證據才顯示，前面用到這個詞的段落拿不到說明。四本書（Claude 讀、ADR-073 補漏後）140 個定義裡 80 個在詞第一次出現 200 段以後才顯示，約 829 段用到某個術語時看不到定義。
- 決定：同一個詞可以有幾筆定義（最多 3 筆），各自從自己的位置起顯示；查詢照舊取「到這個位置為止最新的一筆」。資料表改成 `UNIQUE(book_id, source_term, revealed_ordinal)`（migration 32）。模型對同一個 `ref` 可以答幾筆，每筆只寫到它引用的證據為止已揭露的意思、各自引用證據；後一筆要完整（含前一筆仍成立的部分）。提示詞要求：詞第一次出現就看得出一部分意思時，第一筆只用那裡的證據寫那一部分。程式逐筆檢查引用（引用沒給過的那一筆單獨退回）；同位置的保留後答的；超過 3 筆留第一、中間、最後。人寫的定義取代該詞所有模型階段。網頁術語卡把同一個詞的幾筆依位置列出。
- 實測（四本書，只重跑術語這一步，Claude 方案）：第一版提示詞模型很少分段，看不到定義的段落 829 → 967（多定義了 10 個詞）；加上「第一筆從最早的例句寫起」後 829 → 569（−31%，154 個詞、183 筆）。30 個分段的詞、62 筆，評審（Opus）判定 1 筆提前透露後面才揭露的資訊、4 筆兩可、沒有沒用的；17 筆「依據偏弱」多半因為評審只看到含這個詞的段落，沒看到定義也引用的事實。
- 限制：定義只給譯者理解原文，不會印進書裡，所以提前透露的影響是譯者可能把後面的資訊寫進前面的譯文（翻譯規則 4 禁止）；仍有約 569 段用到術語時沒有定義（詞在書裡前面確實還看不出意思的，本來就不該有）。
- 同時決定不做：規則確認的「待查」狀態（目前不確定的本來就送審稿，沒看到因此出錯）、事實證據跨段（四本書 44 筆證據被退回裡只有 8 筆是證據分散，約占全部事實 1%）、一個字的人名（四本書沒有一字人名進譯名表，記成角色的一字詞多是一般名詞）。之後遇到實際問題再做。

## ADR-076（2026-10-20）：共用規則片段、標點照原文、規則衝突偵測、舊意見由後一輪取代
- 背景（整本實測，奇幻愛情）：原文用『』標出稱號（『賢者』），翻譯提示詞要照原文保留引號，校稿卻要求敘述中的外層用「」（臺灣出版慣例）；官方中文版保留『』。校稿為此送修 33 次，很多次譯者交回一模一樣的文字、修正驗收判「仍然錯」，最後全書有的「」有的『』。另外第一輪沒修好、第二輪修好的段落，第一輪的意見一直是「未解決」。同一條規則在翻譯與檢查的提示詞各寫一份，說法慢慢分岔，是拉扯的來源。
- 決定：
  - 提示詞可以引用共用片段（`<!-- include: 名稱 -->`，`prompts/_shared/`，載入時展開，展開後才算版本雜湊）：`judgement_order`（判斷順序）、`addition`（多加的判準）、`punctuation`（標點）。測試：檢查步驟引用的共用片段，翻譯也要引用（沒有例外清單）。
  - 標點照原文（使用者：「標點符號該是什麼就是什麼」）：原文的「」譯「」、『』譯『』，不因臺灣慣例改種類，原文沒有的引號不加；刪節號、破折號、全形標點與縮排由程式統一。校稿的 `style` 只回報引號與原文對不上（漏、多、種類換了）或同段內不一致。體例不得寫引號規則。
  - 規則衝突偵測：送修後交回的文字和原本一樣（程式排版後比對），不送修正驗收；模型提出的意見改為 `conflict`，另記一筆 `rule_conflict`（類別與理由），同一次執行裡同一段、同一類不再送修。驗收與網頁把衝突另列，不算未解決的錯；但關於原文意思的嚴重問題（`SOURCE_CLAIMS`、high）不算衝突，照樣留給人。
  - 舊意見由後一輪取代：一輪校稿（或讀者檢查）真正看過某段目前的版本、沒有再提出同一類問題時，這段舊版本上未解決的意見改為 `superseded`；被擋、失敗的段落不算看過。驗收與網頁只算關於目前版本的意見。
- 實測（三個模型各校兩輪，同一本前 195 段，從整本實測的譯文開始）：引號與原文對不上的段落 22 → Claude 11、Codex 0、Gemini 3（從整本來的；重新翻譯時譯者與校稿已一致，不會再產生）；被取代的舊意見每輪 6–14 筆；沒有出現規則衝突。Codex 校稿提出的 22 處引號問題都被修正驗收判為不必改（不採用，只多花請求）。

- 背景（整本實測，奇幻愛情，Claude 方案）：校稿、審稿、讀者檢查找到問題後的修正重譯有 136 個請求，平均每個 21,500 個輸入 token 只改 1.1 段，照定價比整本初次翻譯還貴（US$17.9 對 17.4）。修正請求附的是整場的資料（`whole_scene=True`：整場的人物卡、記憶、稱呼，前後各 2,500 字）。
- 決定：修正請求改用「修改範圍」（`translation.fix_scope: window`，預設；`scene` 是原本的做法）：前後各 `translation.fix_context_chars`（1,200）字的原文與現行譯文（每邊至少兩段，不跨場景）；人物卡只給範圍內說話、被叫、被提到名字或是省略主詞動作主受詞的人（範圍內出現就算，名字與性別以範圍最後一段的位置為準，所以後面幾段才提到名字的人也有卡）；第一人稱的敘述者；稱呼只限這些人之間；事實 `context.fix_fact_quota`（4）筆、本章摘要只最後一筆、不附上一章回顧；譯名、術語定義、雙關與口吻只看範圍內的文字；台詞與動作的分析只附要修的那幾段（範圍內其他段的分析占修正請求三成，原文與譯文已經在前後文裡）。每個請求的資料字數記在 `usage.payload_chars`。

## ADR-079（2026-10-21）：請求資料的精簡格式；場景台詞照故事順序
- 背景：翻譯請求附的資料（場景分析、事實、稱呼、人物卡）占大半。原本估計場景台詞裡重複的長段落編號很占空間，實際上 `ShortIds` 早已把請求裡所有內部編號換成短代號（先前的量法是在編碼前量的）。另外發現場景分析的台詞是依段落編號（雜湊）排序送出的，不是故事順序。
- 決定：`translation.compact_payload`（預設開）：一段只有一句台詞時不寫 `quote_index`；說話者是原文寫明的不寫 `status`；台詞 `quote` 只節錄前 16 字；事實的原文依據只節錄 60 字內、保留關鍵詞；人物卡的已證實台詞每人最多 2 句；稱呼表不寫 `since`（本來就依首次使用排序）。翻譯、審稿、校稿、修正驗收的提示詞說明這些省略與節錄。台詞與動作的分析改依段落的故事順序送出（兩種格式都是）。

- 限制：省得不多。台詞裡的說話者仍寫全名，換成人物代號是下一個較大的空間，但會讓譯者多一層對照，沒有做。

## ADR-080（2026-10-21）：稱呼規則寫明指誰；名字記下原文的讀音
- 背景（校園日常第二集抽查，Codex）：體例寫出「稱呼『安達さん』譯為『安達女士』」——書裡「安達さん」既是島村的母親叫安達的母親，也是島村開玩笑叫同學安達；沒寫指誰的規則先被定名照用（島村→安達也定成「安達女士」），再被翻譯照用，同學之間的玩笑譯成「安達女士」。另一次執行寫成「稱安達母親的『安達さん』…」就是對的。另外，定名的例句是去掉讀音的原文，譯名表與人物卡也沒有讀音，讀法特殊的名字（彩葉《いろは》）定名時看不到作者指定的讀法。
- 決定：
  - 體例：關於名字、稱呼、敬稱的規則要寫明指誰（譯法因說話者而不同時也寫明誰說）；同一個寫法在書裡指不同的人時，不寫成規則，由譯者逐句判斷。
  - 翻譯：稱呼的規則只適用於它寫明的人；和稱呼表（誰怎麼叫誰）衝突時以稱呼表為準；規則沒寫明指誰、而這裡指的是別人時，依這一句判斷。稱呼的既有譯法是平常的預設，這一句的場合、情緒或用意明顯不同（爭吵、嘲諷、開玩笑或捉弄、刻意客氣或刻意親暱、正式場合、偽裝）時依原文調整，譯出那個刻意的效果。
  - 讀音：程式從原文的讀音標註收集每個譯名表詞條在書中標註過的讀音（只看完整標在這個詞上的，依首次出現排序；`glossary.readings_json`，migration 33），讀完書與定名前更新。定名的例句改用模型讀原文時的樣子（漢字《かな》）；定名、翻譯的譯名與人物卡、校稿的人物卡附 `readings`；網頁的譯名、角色頁面顯示讀音。讀音的假名不寫進譯文，讀音帶另一層意思時照 ruby 的規則處理。
- 實測：重跑體例兩次，規則都寫明指誰；校園日常第二集前 400 段用新程式從頭跑（Codex）：定名把島村→安達的「安達さん」定為「安達同學」、叫安達母親的仍是「安達女士」，§368 譯成「安達同學，妳裙子裡面都被看光光了喔～」（同官方版）。《超かぐや姫！》重跑定名，譯名表記下彩葉《いろは》、真実《まみ》、紅葉《もみじ》、酒寄《さかより》等讀音。
- 限制：讀音不依故事位置過濾（後面集數才標的讀音前面也看得到）；只收完整標在詞上的讀音；人物沒有譯名表詞條時沒有讀音。


## ADR-081（2026-10-21）：敘述定下的性別算寫明、全書補問性別；引號依意思；同形詞檢查；逐段判定的輸出格式
- 背景（Codex 抽查四本書各 400 段，對照官方版）：校園日常第一集 12 處對女生用「你」——讀書只記到日野一個人的性別（推測），安達、島村、永藤沒有性別，翻譯照規則用「你」。小錯裡「二学期」照搬成「二學期」（臺灣指春季學期）、「応接室」照搬成「應接室」；引號一律照原文，原文用「〜と言う」帶出的話、「という表現」提到的說法也不能加引號。同一個模型讀原文就讀偏的錯（§389「ので」接錯、§224 敘述口吻變成角色自稱），校稿怎麼寫都抓不到（見下）。
- 決定：
  - 性別：讀書（`scene_read`、`memory_update`）與補問（`gender_gaps`）把「敘述本身定下性別」算原文寫明（`explicit`）：帶性別的身分或角色（女子高生）、穿只屬於一種性別的制服或衣著（制服的裙子）、身在只限一種性別的場所或團體、敘述把他算進只有一種性別的一群人；仍要逐字引用原文。只靠自稱或口吻（あたし、～わ）的仍是推測；化妝、髮型、興趣等刻板印象單獨不算。第一版把這類描述記成推測，翻譯照規則（推測→「你」）仍是 12 處「你」。
  - 補問性別（`context.gender_gaps`，預設開）：讀完、第二次確認之後，說過 3 句以上或被提到 8 段以上、仍沒有性別的人物，附全書分散的原文 8 句（他說話、被提到、被叫的段落，各有代號）一次問模型（每請求 10 人，stage `verify:genders`）；只收引用了給它的句子的答案，`unknown` 不記。找句子是字面與記錄比對，判斷是模型的事（ADR-059）。
  - 引號依意思（`_shared/punctuation.md`）：預設照原文；原文用「〜と言う／って／という」標出的話或說法，中文加「」標出可以；敘述、沒有說出口的念頭不加。程式規則 `quote_mismatch` 多一對或少一對引號改為 high 並交模型依前後文確認（`CONFIRM_RULES`），只有種類換了才是 low。
  - 同形詞（`context.false_friends`，預設開）：初譯完、校稿前，程式找出原文的漢字詞原樣出現在譯文裡的（OpenCC `jp2t`→`t2tw` 轉成臺灣字形；沒裝 `opencc` 時只用程式的短表），最常見的附兩個例句問模型哪些在臺灣意思不同或不自然；模型判定不同的記一筆未確認的譯名（附理由），帶這個詞的段落送回譯者修正、照常驗收。新增相依套件 `opencc`。
  - 逐段判定的輸出格式：`context.proofread_verdicts` 的提示詞前面要 `checked`、最後的「輸出」卻只寫 `{"issues": [...]}`、「沒有問題就輸出 {"issues": []}」，模型照最後一句做，每本約 390 段裡 200–390 段沒有判定。改成要逐段判定時輸出格式只有一種（含 `checked`）。
- 實測（Codex gpt-6.1-sol，從頭跑前 400 段）：校園日常第一集用到第二人稱的 23 段全部是「妳」（改前 12 處「你」）；四個女生都記成寫明、附原文（「どっちも制服だから…スカートが捲れ上がって」「同級生の女子が…日野と永藤が」）。「二學期」→「第二學期」、「應接室」→「會客室」；同形詞第一集 150 個詞判 3 個不同、奇幻 195 個判 3 個。引號第一集多加 8 處、奇幻 1 處，都是「〜と言う」「という」帶出的話，沒有加在敘述或念頭上。
- 校稿實驗（同一個模型，四本書各約 390 段，11 個已知的錯，修好格式後）：原本的校稿 0/11；逐段寫一句摘要 2/11；逐段先只看原文寫「聲音、關係、語氣」再對照 2/11（同樣兩處：a2 §163、§183 多加的引號）；後兩者輸出 token 約 2–2.5 倍。結構寫法看得出原因：模型寫下的原文理解本身就錯（§224 寫成「酒寄式自我介紹；請讀者稱呼自己」、§389 沒有分析「ので」），換寫法只是把錯的理解寫出來。不改校稿的預設；這類錯換另一個模型讀才看得出來（Claude Opus、Gemini 3.8 Flash 重翻同樣場景，§30、§224 都對）。
- 限制：補問性別只問說話或被提到夠多的人；性別依據的是描述時，女裝等設定可能判錯（之後的描述與檢查仍在）。同形詞只看原樣照搬的漢字詞，字形不同的誤用看不到。

- 背景：同一個模型讀原文就讀偏的地方，它自己校稿看不出來（ADR-081 的校稿實驗：四種寫法 0–2/11）。抽查四本書各約 390 段：Sol 翻錯、校稿也沒抓到的段落，Claude Opus 與 Gemini 3.8 Flash 重翻時多半是對的。Antigravity CLI（`agy`）能用使用者的 Antigravity 方案跑 Gemini（Flash、4 Argon）與 Claude、GPT，不經 OpenRouter、不另付費。

## ADR-083（2026-10-21）：敘述片段——場景裡換成另一個聲音的幾段
- 背景（《超かぐや姫！》抽查）：§220–227 是夾在彩葉第一人稱場景裡的仿《竹取物語》說書旁白，§224「──彩葉って呼ぶべし♪」被譯成「叫我彩葉就好♪」；§113 是彩葉想起的媽媽的話（「──今でも彩葉はすぐに泣いて帰ってくると思ってます、甘ちゃんやから」），譯成「畢竟妳就是太天真了」。讀書時的敘述方式（`narration`）是整個場景一個值，這場記成「第一人稱，敘述者是彩葉」，翻譯照規則把「我」給了說書人。這是資料不夠細，不是模型不懂。

- 實測（Codex，從頭跑前 400 段）：《超かぐや姫！》記下 §109、§113、§146、§285–286（回想中的媽媽的話，說的人：媽媽）、§220–227（仿古說書旁白，說的人沒交代，在講別人）、§245（醉漢）、§402、§415；§224 譯成「——叫彩葉就好囉♪」，§113 譯成「……畢竟還是個天真的孩子嘛。」（沒有選「妳」或「她」）。奇幻那本沒有記任何片段。讀書的輸出 token 多 1–5%。
- 限制：只看讀書時判斷的片段，判錯會帶到那幾段（附證據）；第二次確認還不覆核片段。

## ADR-084（2026-10-21）：兩可的讀法——校稿可送修成不選邊的寫法；對某些人說話的方式
- 背景：§113 是對彩葉說還是對別人說，原文不足以判定（全書 §2830 媽媽當面對彩葉也用諷刺敬語），較好的是不選邊的寫法。規則互相拉扯：「多加的判準」說把原文沒確定的人寫死算增譯；校稿的 `ambiguity` 說原文容得下目前的讀法就是兩可、只留給人看，從不送修；翻譯收到修正時「原文容得下目前的讀法，維持原譯」。三位顧問（gpt-6-astra、Gemini 4 Argon、Fable）審過草案。
- 決定：
  - 校稿 `ambiguity`：另一種讀法要在原文與前後文有根據，`problem` 寫出查過哪些資料仍排除不了；中文寫得出兩種讀法都成立、一樣自然、意思與語氣不少的譯法，而目前的譯文選了其中一種時，`fix` 寫那個不選邊的譯法、`severity: medium`，送去修正（提示 `FIX_NOTE_AMBIGUITY`）；寫不出來或非選不可時 `low`，照舊只留給人看。已經沒選邊的不回報；選的是原文容許的其中一種讀法時只歸這一類、不另報 `addition`。
  - 翻譯收到 `proofread_ambiguity` 的修正：改成兩種讀法都成立的寫法（不是換成另一種讀法），寫不出自然的就維持原譯並在 `notes` 說明。修正驗收：不選邊的寫法不算「另一種讀法」；自然、沒丟意思與語氣判 `fixed`，為了不選邊讀不順或丟了語氣判 `still_wrong`。
  - 人物印象 `voice_toward`／`toward_evidence`：對某些人說話的方式和平常明顯不同、反覆看得到時寫出（要附證據），從第一個證據的位置起才給譯者與校稿（migration 34）；提示詞寫明不能單憑說話方式斷定對誰說。
  - 敘述片段多記 `addressee_ref`（ADR-083）。
- 初譯不改（實測後撤回）：曾把「能不選邊就不選邊」寫進翻譯與檢查共用的判斷順序、把「選了原文容許的讀法不算多加」寫進共用的多加判準。重翻 200 段（Codex，盲評 Gemini 4 Argon，附前後各五段的原文與譯文）對照舊規則重翻：人稱省錯或補錯 對照 0、新規則 5；兩處都撤回、只留在校稿之後 1（輕微）。「舊譯較好且新譯有錯」對照 3、撤回後 8，但其中 §157、§278 對照組譯出同樣的句子而評審沒判錯，評審本身的出入占了大半。
- 實測（校稿，Sol，四本書約 1,557 段，一輪）：只提出 8 個問題，兩可送修 3 處（0.2%）：§113 由 Sol 自己抓到並修成「……畢竟就是太天真了嘛」；a1 §250 拿掉自己補的「我」；a2 §237 是本來就沒選邊的白報一次。
- 限制：`voice_toward` 只在重新讀書或重跑印象時才有；不選邊的寫法只在校稿之後產生，初譯仍可能選邊。

## ADR-088（2026-10-21）：覆核看得到完整證據段落；空答案重問；性別依據的種類
- 覆核：被問的段落與讀的階段引用為證據的段落給全文（上限 2,000 字）；不在前後 4 段內的證據段落另外附上，最多 3 段。其他前後段落只給開頭 200 字。

## ADR-090（2026-10-22）：讀後整理的請求同時送、答案隨到隨存
- 背景：讀後整理（覆核、補問性別、人物關係、角色印象、術語定義）每一步先把請求準備好，卻一個一個送，答案留在記憶體，整步做完才寫入；中途暫停，續跑時整步重問。2026-10-21 agy 整本中，這幾步約 54 分鐘。
- 決定：每一步從同一份筆記快照準備好全部請求，同時送 `max_concurrency` 個（ADR-065 的 `_side_by_side`，`_ask_groups`），被內容審查擋下的照舊拆半。全部回來後依請求原本的順序寫入，與一個一個送的結果相同。每個答案一回來就記在 `llm_requests`；同一次執行裡內容相同的請求直接用記下的答案（`Recorder.answered`、`call_structured(reuse=True)`），不再送出。暫停時這一步不寫入，續跑時快照相同、請求相同，只送還沒有答案的請求。帶修正說明的重問不沿用舊答案；新的執行一律重問。
- 依賴照舊：人物關係先於角色印象，角色印象先於全書寫法；人物關係的「再問一次」等第一輪回來才送。全書寫法、定名只有一個請求，不變。
- 預期：讀後整理約 54 分鐘 → 同時 2 個時約 30 分鐘（需實測）。

## ADR-093（2026-10-22）：覆核也問「讀書推測、做的人不在場」的動作；不先給舊答案
- 背景：§3211「〜って言われて」的說話者，讀書時記成爺爺（推測），翻譯、校稿、驗收都照用「他」。同一個模型在讀場景的請求裡 6 次都錯（全部人物卡、只給出場的卡、只給前 12 段都一樣；證據與母親的卡都在請求裡），單獨問這 9 段卻答得出是母親（§3216「抱不到孫子」對祖父母是曾孫；§3218 母親的說教郵件）。原因不是資料不夠，而是那一項在很長的請求裡沒被仔細想過。三位顧問（Astra、Gemini 4 Argon、Fable）都建議先擴大單題覆核。
- 決定：覆核另外挑出標為推測或未知、做的人不在這一場（不是參與者、說話者或敘述者）的動作，每本最多 `context.verify_action_items`（預設 40）個。每一項附這一場從開頭到結尾的全文（段落代號、上限 8,000 字，不超過場景結尾）；**不給讀書時的答案與摘要**，避免順著舊答案答。模型回答做的人、依據的段落代號與一句新的摘要；程式只核對代號確實送出、人物 id 存在，然後改寫動作（保留改前、理由、證據）；改過的仍是推測，不升成確定；改過的不再重問，直到這一場重讀。翻譯與校稿的人物卡跟著新的動作走（ADR-086）。
- 實測（agy Flash，整本副本）：全書挑出 4 項，3 項維持；§3211 爺爺 → 紅葉（兩次一樣，Opus 判斷正確），翻譯請求的人物卡從爺爺換成紅葉。先給舊答案的版本，模型照舊答爺爺。

## ADR-094（2026-10-22）：讀後整理的請求和之前某次執行完全相同時，沿用那次的答案
- 背景：只重讀一場時，讀後整理（覆核、補問性別、人物關係、角色印象、術語定義）會對整本重跑；ADR-090 只在同一次執行裡沿用答案。2026-10-22 只重讀一場的實測用了 75 個 agy 請求，大部分花在這裡。
- 決定：`request_hash` 涵蓋模型、完整訊息（提示詞文字與資料）、格式、推理等級；同一本書、同一步驟、雜湊值相同且之前成功的請求，直接用那次的答案（同一次執行的優先）。存下的答案解析不了照樣重問；帶修正說明的重問不沿用。`context.reuse_answers: false`、`--fresh`、`--force` 不用之前執行的答案。沿用的答案不新增請求紀錄、不算作模型新看過什麼（ADR-055）；每一步在紀錄寫一行沿用了幾個。只用在讀後整理（`_ask_groups`），翻譯與校稿不變。
- 限制：提示詞改過之後全部重問（正確，但改版後第一次重讀不會省）；一場重讀會改到很多批次共用的人物卡與筆記，實際能省多少要等同一版程式重讀時才知道（這次的重跑跨了 ADR-085～093 的改版，一個也沒對上）。

## ADR-095（2026-10-22）：親屬詞帶出日文沒寫的一層，依紀錄決定，沒有紀錄就不選邊
- 背景：§3211「お祖父ちゃんお祖母ちゃんとこ」，正常流程重跑時譯成「外公外婆」；書裡 §979 寫「父方の祖父母」、§981 寫母親被自己的父母拋棄，應是爺爺奶奶。人物關係的證據裡已有這兩份材料，但卡片只寫「祖父」；翻譯從「說話的是母親」推成母親那邊。日文口語的祖父母、兄弟、おじさん不分父系母系或長幼，中文的親屬詞常要多決定一層。
- 決定：
  - 人物關係：材料寫明父系母系、長幼或姻親時寫進 `a_is`／`b_is`（「祖父（父親那邊）」）並附上那份材料；沒寫的不猜。
  - 翻譯：真的親屬時，這一層照 `characters[].relations` 與 `memory` 決定；沒有說明時用不帶這層資訊的說法（祖父母、兄弟、長輩），不從說話的人或場面猜。
  - 共用的多加判準（`_shared/addition.md`）：紀錄沒說明那一層卻選了一邊，算多加；翻譯、校稿、審稿讀同一段文字。
  - 校稿的人物卡附上這一段人物彼此的關係（到這一段開頭為止，每人最多 4 條）。
- 實測（agy Flash，重跑那一場的副本，4 個請求）：人物關係只重問這一對，答「祖父（父親那邊）」並引用父方那份材料；§3211 重譯，關係寫明父方時譯「爺爺奶奶」，只寫「祖父」時新提示詞譯「祖父母」（舊提示詞譯「外公外婆」）。
- 沒做：翻譯請求的事實挑選不改（加權後 §981 仍排不進來，反而把無關事實往前推）；改由關係標籤帶這一層。已讀的書要重跑人物關係才會有新標籤。

- 背景：讀書推測判斷的抽樣（68 題，Opus 單題重問、盲評）錯誤集中在動作「誰做的」。兩處錯誤的摘要本身沒錯，但一筆裡混了兩個人做的事：§2284 摘要寫彩葉「被對方用美麗神情說得無言以對」，做的人卻照另一個動作填成說話的輝夜；§2509 摘要寫「八千代報告輝夜很高興」，誰對誰說話已記在台詞表，省略主詞的其實只有「誰很高興」。原因在提示詞：`actions` 是「列出……的句子」，一句一筆，同一句裡兩個人各做一件事時只能擠成一筆。

- 實測（5 本書 16 場、18 個請求，同一份請求內容只換提示詞；Opus 盲評，每場兩份動作表隨機標 X／Y）：
  - agy Flash：一筆混了兩個人的事 5/52 → 0/64；做的人錯 0 → 1（把台詞裡的疑問當成發生了的動作）；整場較好 舊 7、新 6、差不多 1；每場平均筆數多約四分之一。§2509 新版寫「輝夜感到很高興」、做的人輝夜。Gemini 每週額度用 3%。

  - 評審在兩版都指出：每場只列 0–8 筆，許多主詞省略、容易譯錯的動作沒有列（例如經典第一人稱小說裡別人替「我」做的事）。這是收錄範圍的問題，不在這次修改內。
- 沒做：不靠程式比對摘要和做的人（ADR-059：意思由模型判斷）。

- 背景：agy 整本 14 小時，其中校稿 5 小時 21 分；同時送的請求數一直沿用 `max_concurrency` 預設 2。

## ADR-098（2026-10-22）：校稿標 partial 時，續跑只補沒判定的段落
- 背景：ADR-089 之後，逐段判定時沒判定的段落留紀錄、這一輪標 partial，但續跑（`ncte resume --run-id`、網頁的「繼續」、`ncte agent resume`，都是接著同一個 run）看到校稿不是 pending／running 就跳過；要補只能整本重跑校稿。執行結束的 run 在網頁上也沒有「繼續」可按。
- 決定：
  - 每一輪把沒判定的段落 id 記在自己的計數裡（`no_verdict_ids`；兩輪以上記在 `passes` 的那一輪）；暫停時跟著檢查點存。
  - 續跑時校稿是 partial、記有沒判定的段落，就只送這些段落（`_fill_unanswered`）；有判定的段落不再送。相鄰的段落併成一段送，各附前後同一章的段落（各最多 6 段，只讀、不檢查；校稿提示詞多一個 `context_after`，沒有時不出現）。走同一個流程（`_proofread_part`）：沒判定的單獨再問一次，找到的問題送回翻譯、修正對照原文驗收（ADR-055）。
  - 有判定的加到那一輪（`checked`、`verdicts_filled`、送修與驗收的計數）；`sent` 不變（那一輪已送過）。仍沒判定的留在清單、各留一筆新紀錄，舊紀錄標 `superseded`；請求失敗或因暫停沒送出的，段落留在清單、舊紀錄不動。被內容審查擋下的不再列入清單，算進那一輪的 `blocked`（照舊不重問）。
  - 每次續跑補一次，同一次執行裡不重複；清單補完、之前也沒有擋下或失敗的，校稿改成 succeeded，可驗收的「校稿完成」跟著通過。
  - 輪次的順序：每一輪的缺口用那一輪自己的步驟補（最後一輪選了交叉校稿就用交叉校稿的模型），依輪次順序。第二輪已經看過、第一輪沒判定的段落，仍補第一輪：每一輪是一次獨立的檢查，後一輪看過不代表前一輪看過（ADR-055）。後一輪的計數不動；`upto_translation_id` 不動，補問時重譯的段落下一次新的 run 會再校一次。補問的修正發生在後一輪之後，由修正驗收把關，和最後一輪的修正相同；讀者檢查已做完的不重做。
  - 網頁：執行已結束但校稿有沒判定的段落時，顯示段數和「補問沒判定的段落」，按下去就是續跑。
- 限制：新開的 `ncte translate`（新的 run）不接手舊 run 的清單，照舊從上一次完整的校稿之後重校。

## ADR-099（2026-10-23）：提示詞直接說任務，不設身分；翻譯與讀者檢查不寫「輕小說」
- 背景：16 個提示詞以「你是……」開頭。多數只有名稱（小說的編輯、譯者、覆核者），下一句已說清任務；翻譯寫「專業的日文輕小說譯者」、讀者檢查寫「台灣的輕小說讀者」，等於替所有書先定了文體，而送進來的書已有近未來科幻、奇幻、宮沢賢治的童話。書的類型與口吻由讀完全書的體例步驟判斷。

- 限制：各步驟提示詞版本改變，之前記下的答案不再沿用（ADR-094）。樣本小，只有 agy Flash。

## ADR-100（2026-10-23）：修正驗收沒有回答的，同一次執行再問一次，續跑時補問；空答案的重問所有步驟共用
- 背景：agy Flash 整本（銀河鉄道の夜，2026-10-22／23）最後 8 段 `needs_review`、可驗收「還沒」，全是修正驗收沒有回答：同形詞那一步的 3 個 `fix_check` 請求（7 段）回 `EmptyAnswerError: empty answer`，記了一筆 `fix_check_failed`（「N units: empty answer」）就沒有再問；1 個請求（2 段）被暫停（SIGINT）打斷，`ncte resume --run-id` 之後也沒有再問，`fix_unchecked` 一直開著。校稿沒判定的段落會單獨重送（ADR-089），補問性別遇空答案會重問（ADR-088），修正驗收兩樣都沒有。agy 大約一成的請求回空答案。
- 決定：
  - 空答案的重問移到 `call_structured`（`translator.EMPTY_RETRIES`，3 次，原本只在 `ContextOrchestrator._llm`）：所有經過它的步驟都一樣重問——翻譯、審稿、修正驗收（含 `ncte eval` 的修正驗收）、讀書與讀後整理（分析、整理記憶、覆核、補問性別、人物關係、角色印象、術語）、規則確認、同形詞、校稿、讀者檢查。`_llm` 不再另外計數；空答案仍不帶修正說明再問。
  - 修正驗收：重問空答案之後請求仍失敗，或答案漏了某些段落，這些段落各自單獨再問一次（同 ADR-089）。只有一段的請求失敗時不再問（會是同一個請求）。被內容審查擋下的照舊拆半，不再問。失敗的請求，它的段落後來都問到答案時，那筆 `fix_check_failed` 標 resolved。
  - 修正寫入時，同時記下驗收需要的東西（migration 36 `translations.fix_json`）：被換掉的譯文（id 與匯出的文字）、送去修的問題（含 finding id）、程式規則在新譯文找到的問題。原本這些只在記憶體裡，修正與它要結案的問題之間在資料庫沒有連結（`fix_unchecked` 只記新譯文的 id）。
  - 執行完成之前（翻譯、續跑、只審稿、只校稿、只做讀者檢查的執行；暫停或停下時不做），還在等驗收的修正（`fix_unchecked` 開著、仍是書裡的那一版）用記下的資料再問一次，一場一場問，走同一個驗收與結案流程（`_settle_fixes`：fixed、issue_invalid、still_wrong、regressed…），結果與第一次就回答相同。同一個程序裡已經問過的（第一次與單獨再問）不再問；已回答的本來就不在等。後來審稿沒找到問題而把 `needs_review` 清掉的，仍要驗收；驗收沒結案時改回 `needs_review`。
  - 仍沒有回答：照舊開著（「…（asked again after the run; still no answer）」），不算檢查過（ADR-055），可驗收維持「還沒」。下一次續跑或新的執行再問一次。
- 限制：migration 36 之前寫入的修正沒有這份紀錄，無法補問（`unrecorded` 計數），保持開著；那本書的 8 段要重跑那一步或重新匯入（舊書是測試資料，不做補救）。翻譯批次遇到空答案時，每次嘗試各自重問最多 3 次，之後照舊帶修正說明再試、再拆半，請求數可能比以前多。

## ADR-101（2026-10-23）：讀音也是原文；沒有名字的人物以原文的寫法建卡
- 背景：讀書推理程度 low／medium 的步驟抽驗（奇幻輕小說那本 10 場，`workspace/exp/low-reading`）在 `memory_rejections` 留下兩種不是模型讀錯、而是程式核對證據時漏掉的拒絕：
  1. 讀音看不到：核對「字句在原文」（`in_source`）只比對去掉讀音的文字。原文只以讀音寫出的詞——〝下級精霊《ローエレメンタル》〟的「ローエレメンタル」、【火《サ》の《ラ》下《マ》級《ン》精《ダ》霊《ー》】每個字的讀音連起來的「サラマンダー」——都算「不在原文」：low 那邊 2 筆譯名表候選、1 筆名稱連結被拒。
  2. 沒有名字的人物整張卡被拒：模型替原文沒有名字的人取了描述性名稱「人攫いの指示役の男」（原文沒有這幾個字），別名「一番後ろにいた男」「指示を出していた男」卻是原文逐字；程式只看 `name_ja`，整張卡以「可能是捏造」拒絕，他的台詞候選、說話者、在場紀錄、動作的人物跟著變成「不認得的代號」被拒（兩邊各約 20 筆）。下一場模型以原文的「指示を出していた男」為名，但證據只引這一場（那幾個字在上一場），又被拒。
- 決定（ADR-059：程式只核對字句在不在、位置與可見性，不判斷意思）：
  - 讀音：`units.read_text` 是把每個讀音放在它的本字位置讀出的文字（逐字的讀音連成一個詞）；`in_source` 在去掉讀音的文字或 `read_text` 裡找到都算原文。兩種寫法是分開的兩份（`units.text_forms`），各自找、不接成一串；讀場景時也是一段一段找：本字的結尾接讀音的開頭（只有 強敵《とも》 的段落拼出「強敵とも」）、兩段之間拼出的字串都不算。讀場景與整理記憶所有核對字句的地方都經過它（道具與名稱連結的字詞一段一段找，不把整場接起來）（人名、別名、其他寫法、道具、發話字句、事實與關係的引文、譯名表、名稱連結、稱呼、雙關、性別、群體）。讀場景的核對改用存下來的原文（含讀音），不再用去掉讀音的文字。存下的是模型給的寫法：以讀音給的詞存成讀音（`ローエレメンタル`）。本字和讀音混在一起（「火のサ」）兩邊都不是，仍拒。
  - 譯名表裡以讀音寫的詞要能用到：選哪些譯名表條目附給請求（`cache.relevant_glossary`：翻譯、審稿，與只算已確認條目的快取鍵）、讀場景與整理記憶附的譯名表，改在 `units.text_forms`（去掉讀音的文字、`read_text`，各自找）裡找。
  - 不變（照舊只看去掉讀音的文字）：`match_text` 本身；程式品質檢查（`qa/rules.py` 的譯名一致等：以讀音寫的詞不要求譯文出現它的譯名，一組本字與讀音在中文只譯一次，譯哪一邊是譯者的判斷）；定名的例句、術語步驟的次數統計、同形詞、性別缺口、印象、體例的字串比對。
  - 沒有名字的人物：`name_ja` 不在證據段落時，先看別名：有原文逐字出現在證據段落、至少兩個字的別名（模型標 `name` 的優先，其次暱稱、稱號、描述；普通名詞與代名詞不算；一個字的「男」沒標成普通名詞也不算，和其他寫法的兩字規則相同），這張卡就以那個別名建立（其他別名照舊）。模型自己取的稱呼不是原文，不當名字也不當別名；它的中文提案是那個稱呼的譯法，不是這幾個字的，也不存（不寫進卡上的中文名、不建譯名表），卡的譯名和其他描述性的卡一樣由定名決定。那個稱呼只當模型的描述記在場景的紀錄（`state_json.model_labels`：卡與稱呼），不是證據，不送回模型（整理記憶的請求不帶，`scene.RECORD_ONLY`）、不進譯名表。名字與別名都不在原文，照舊以「可能是捏造」拒絕。
  - 前面場景已知的寫法：`name_ja` 不在這一場的證據裡、但正是這一場開頭以前已看得到的人物卡上的名字或別名（`character_view` 到前一段為止顯示的寫法），新人物就是那張卡（同 `name_ja` 在證據裡、又是已知寫法時的處理）。那幾個字已在讀到它的那一場核對過，位置在這一場之前；之後場景的寫法不會算進來（卡在那之前還看不到）。模型至少要引這一場的一段。只在模型沒說是別人時這樣做：模型標了 `other_person`、`period`（前世的「母親」），或是否群體和那張卡不同，就照模型說的是另一個人；同一寫法屬於幾張卡時程式不替模型選。這兩種都照「寫法不在證據裡」處理（看別名，沒有就拒絕，拒絕理由寫明是哪一種）。對到卡的記在場景紀錄（`state_json.matched_by_words`：模型的代號、寫法、卡）與這一場的計數（`matched_by_words`），看得到程式替模型的新人物對了哪張卡。以別名代替模型的名字、而那個別名正是已知的卡的寫法時，也照模型說的：標了 `other_person` 或 `period` 就另建一張帶時間的卡（同 `other_person` 的處理），是否群體和那張卡不同就拒絕，不併進那張卡。
  - 名字後來揭曉：這種卡和其他描述性的卡一樣，`same_as_ref` 指向它時合併，揭曉前只顯示原文的寫法（ADR-032）。
- 重放（離線、不花額度）：兩邊實際的模型回答（`llm_requests` 的 `scene_analyze`、`memory_update`，依序）先用舊程式在 `base` 的副本上照流程重放一次（每場的統計與原本紀錄相同），記下解完代號的答案；再用舊、新程式各套到新的 `base` 副本上：
  - low：拒絕 24 → 2（不認得的台詞候選 8、說話者 7、在場 2、人物名 2、譯名表 2、名稱連結 1 → 0）。
  - medium：拒絕 23 → 1（台詞候選 8、說話者 7、動作人物 3、人物名 2、在場 2 → 0）。
  - 留下的都是一個字的「父」：模型把「父」報成已知人物的其他寫法（兩邊各 1，規則是至少兩個字），low 另有 1 筆「父」的稱呼被記憶更新的 `len(term) < 2` 擋下。兩條都不在這次範圍內，沒動。
  - 結果：兩邊都多一張「一番後ろにいた男」（別名「指示を出していた男」），兩場 7 句台詞的說話者是他；low 多 2 筆譯名表（ローエレメンタル、レッサーデーモン）與「火の下級精霊 → サラマンダー」的名稱連結（サラマンダー還沒有譯名表條目，照舊記為候選）。
- 審閱後修正（同日，合併前）：第五輪：這一場以前沒有一張卡有這個寫法時，後面才出現的卡只有一張有它才是它（同一個人提早出現）；兩張以上同樣拒絕，不再由 `alias_map` 取一張往前移。第四輪：同一寫法屬於幾張卡，只看這一場開頭以前看得到的卡（同 `known_by`）；後面才出現的卡不讓它變得有歧義，看得到的那張就是。只寫了時期（`period`，沒有 `other_person`）也當成另一個人（提示詞只為另一個人要時期），和其他情況一致。所有卡的對照（`alias_map`）照舊包含後面才出現的卡：只有它有這個寫法時，就是同一個人提早出現，卡改成從這裡起看得到（原本的設計）。第三輪：同一寫法（模型給的名字本身，或代替名字的別名）屬於幾張卡時不替模型選，拒絕並寫明理由（原本取最早的那張；模型說是另一個時間的人照舊另建一張卡）。第二輪：以別名代替名字時也照模型說的是不是別人；整理記憶的道具、名稱連結一段一段找。第一輪：讀音與本字分開找（原本接成一串，`in_source` 去掉空白後跨過接縫也算找到）；別名至少兩個字；前面場景已知寫法的條件（模型說是別人、是群體、幾張卡同一寫法時不對）與紀錄；模型的稱呼只當描述記下。
- 限制：重放用的整理記憶答案是在沒有這張卡時寫的（模型那時看不到他），實際重跑的答案會不同。讀音與本字各找一次，一段文字裡本字與別處的讀音拼成的字串不算。已讀的書要重讀才會套用（舊書是測試資料）。重讀時後面才出現的卡改成從這一場起看得到（同一個人提早出現），它的其他寫法沒有自己的出現位置紀錄、跟著卡的位置，會提早顯示（例如只在後面出現的別名「黒薔薇」）；這在這個分支之前就有，記在待辦，這次沒改。

## ADR-102（2026-10-23）：整本書的步驟有請求沒問到就是 partial、續跑只補那些；同形詞同時送；一批檢查的修正一起驗收；空答案記下用量
- 背景（agy Flash 整本，銀河鉄道の夜，2026-10-22／23 的資料庫）：
  - 覆核的 3 個請求有 1 個（約 20 項）每次都回空答案，從沒問到；步驟記 `succeeded`，只留一筆低嚴重度的 `verify_failed`。人物關係、角色印象、體例、術語、同形詞也是同一個寫法：請求失敗、記一筆低的紀錄、步驟照樣 `succeeded`；可驗收報告只看校稿與讀者檢查，看不出來。只有補問性別（ADR-088）會標 partial，但續跑時 partial 直接跳過，什麼也不補。
  - 同形詞的 5 個請求一個接一個送（13.5 分鐘），修正一場一場做，每場重譯後驗收完才送下一場（32 分鐘，從沒有兩個同時）。
  - 校稿、讀者檢查、同形詞的修正都是一場一個 `_retranslate_with_feedback`，各自驗收那一場：整本 48 個修正驗收請求平均約 2 段，每個請求的時間與思考量幾乎不隨段數變。
  - 27 個空答案的請求沒有 token 也沒有時間：CLI 回了用量，但 `EmptyAnswerError` 在讀用量之前就丟出，`DbRecorder.failure` 也不記用量，這些請求用掉的方案額度在報告裡看不到。
- 決定：
  - **整本書的步驟**（覆核、補問性別、人物關係、角色印象、體例、術語〔含找漏掉的術語〕、同形詞）：請求在重問空答案之後仍失敗，同一次執行裡馬上把它的項目再問一次——這些結果是給翻譯讀的，要在翻譯之前（同形詞本來就在翻譯之後）：分成兩半各送一次（`_ask_groups`；只有一項的請求，和體例、找漏掉的術語這種單一請求，照原樣再送一次，`_ask_once_more`）；第一次就回答的請求內容不變。被內容審查拆半後只有一部分失敗時，已回答的部分留下、不再問，只把失敗的那部分再分兩半問（`call_in_parts(failures=…)`）；兩半之間暫停了，沒送的留給續跑。兩半裡仍失敗的項目才是沒問到；步驟記 `partial`，沒問到的項目記在檢查點（`unasked_ids`：覆核的 ref、角色 id、配對 `a|b`、術語、詞；體例是整個請求、找漏掉的術語記成一項），計數多一個 `unasked`，那筆失敗紀錄改成 medium 並寫明幾項沒問到。
  - **內容審查擋下的不是沒問到**（再問也一樣被擋）：不列入清單、不讓步驟 partial、續跑不再送；每一步都記一筆 `<步驟>_blocked`（low，寫明擋下了什麼），步驟照樣 `succeeded`。原本補問性別擋下會標 partial（清單是空的，續跑也不補，變成死路）、體例擋下會記成沒問到（每次續跑都再送）、角色印象與同形詞擋下沒有紀錄，都改成這樣。可驗收報告列在 `limits`（每筆附理由與說明：已知的限制，不是失敗），不算不通過。之後整步重做時，之前執行的 `_blocked` 紀錄標 `superseded`（同形詞只看上次之後新譯的段落時不算整步，之前的照舊列著）。人物關係的拒絕以配對算，第一輪失敗、補問時被擋的配對也是已知限制，不列入清單。
  - 續跑（`ncte resume`、網頁的「繼續」）時步驟是 partial、有清單：只送清單上的項目，用現在的資料重組請求（已回答、或資料已變、不再收得到的項目不送），結果加到原本的計數；問完清單清空、改成 `succeeded`，仍失敗的留在清單（每次續跑補一次）。人物關係只換掉被問的配對的關係（`relations.apply(only=…)`），其他配對的不動；角色印象、術語本來就逐項替換（失敗的那一半的術語保留原本的定義）。同形詞補問時 `upto_translation_id`、`since_translation_id` 照第一次的。後面已經做完的步驟不重做。續跑補到答案時翻譯已經讀過這本書（這次執行已翻譯，或這次不再翻譯、之前的執行翻譯過），記一筆 `<步驟>_after_translation`（low）：翻譯沒有這些答案，校稿與之後新的執行會用到；可驗收報告列在 `answered_after_translation`，不算不通過；網頁「補問沒問到的項目」的說明也寫出來。同形詞本來就在翻譯之後，不記。被擋下或不必問的找漏掉的術語不算補到。這筆紀錄記下當時這本書最新一筆譯文；之後書裡每一段的機器譯文（人改的不算）都比它新時，表示全書已帶著這些答案重譯過，執行結束前標 `superseded`（看譯文 id，不看秒數相同的時間）。
  - **新的執行**：規劃這些步驟時看這一步最近一次不是 `skipped` 的紀錄；是 partial、有清單，就排成要做，只問清單上的（檢查點整個帶過來；這次要重讀書時整步重做）。原本只看更早一次 `succeeded`，排成 `skipped`，partial 留下的項目被蓋過。
  - 可驗收報告多一項 `steps_complete`：這些步驟在這本書最近一次（不算 `skipped`）是 partial 就不通過，寫出是哪一步、幾項沒問到。網頁在執行已結束、有沒問到的項目時顯示項數與「補問沒問到的項目」。
  - **同形詞同時送**：偵測請求改用讀後整理的 `_ask_groups`（`max_concurrency` 個同時；請求內容不變，所以請求 hash 相同、記下的答案照樣沿用，ADR-094；續跑時已回答的不再問，原本會整批重問）。修正：各場的重譯同時送（`_side_by_side`），回來的結果依場景順序寫入，不論哪個先回來。一場遇到致命錯誤（含預算用完），已經回來的各場照樣寫入、等驗收（`fix_unchecked`、`fix_json`，ADR-100 由續跑補問），再把錯誤丟出；校稿、讀者檢查依序重譯時也一樣。
  - **一批檢查的修正一起驗收**：`_retranslate_with_feedback` 收一批檢查（一個校稿或讀者檢查的段落、整個同形詞步驟、一個審稿請求）要修的所有段落，照舊一場一場重譯（`fix_groups`，每場帶自己的記憶），寫完後一起交給 `_check_fixes`（每個請求最多 `FIX_CHECK_BATCH` 20 段，也最多 `review.fix_check_chars` 字：`translation.fix_batch_chars` 的兩倍，預設 16000。一個修正請求最多帶那麼多日文的段落與前後文；驗收同一批修正再讀一次原文與前後文、加上前後的中文，大約多一倍，所以一個驗收請求約等於一個修正請求拿到的量。每段照送出的內容算：原文、改前改後、問題、前後各 5 段的原文與譯文；依故事順序切，單一段超過就自己一個請求。`ncte eval` 的修正驗收照舊只以 20 段切）。校稿與讀者檢查的段落本來就同時跑好幾段，段內的各場依序重譯，不再疊加同時數。ADR-100 等驗收的修正補問也改成一起問。每個修正照舊都驗收；結果、紀錄、`fix_json`、單獨再問一次都不變。
  - **空答案記下用量**：`EmptyAnswerError` 帶 `usage` 與 `latency_ms`；agy、Claude、Codex 三個 CLI 來源在空答案時先整理用量（agy 也讀方案額度）再丟出；`DbRecorder.failure` 把它們寫到失敗的那一列，成本報告與方案用量報告就算得到。重問的次數不變（`EMPTY_RETRIES`）。

## ADR-103（2026-10-23）：幾張卡都有的寫法，新人物另開一張卡、標「可能是同一人」，交覆核問模型
- 背景：ADR-101 之後，讀場景時模型提出的新人物，名字（或代替名字的原文別名）是這一場以前看得到的兩張以上卡的寫法（幾位沒有名字的母親都叫「母親」「義母上」），或沒有看得到的卡、但有兩張以上後面才出現的卡有它時，整筆拒絕：他的台詞、在場、動作跟著變成「不認得的代號」，到覆核前都沒有說話者。和使用者決定：不拒絕，另開一張卡，誰是誰交給模型。
- 決定（ADR-059：模型判斷身分，程式記錄、標示、核對證據與可見性）：
  - **另開一張卡**：卡名是原文的寫法（模型給的名字，或代替它的原文別名），和其他卡一樣當名字、證據比對、名詞表用的寫法；別名照一般規則。模型的 `same_as_ref` 正好指向那幾張卡之一時，就是那張（模型說的）。模型標了 `other_person`／`period` 照舊另建帶時間的卡；剛好一張看得到的卡有這個寫法時照舊就是那張（ADR-101 其他規則不變）。寫法不在這一場的證據、別名也不在、但這一場以前有兩張以上看得到的卡有它時，也另開一張（從模型引的第一段起看得到），不再拒絕。
  - **標籤只用來區分**：`characters.label` 是程式給的編號（做卡時有這個寫法的卡數加一：兩位母親之後的第三張是「3」），網頁顯示成「母親（3）」（`repository.card_label`）。標籤不是原文：不存成名字或別名、不建名詞表、不進名稱連結，也不送給模型（翻譯、讀場景、整理記憶、覆核的請求都沒有）。模型分辨同名的卡靠原文：同一份請求裡名字相同的幾張卡各附 `first_seen`（第一次出現的段落開頭，不會超過卡出現的位置），翻譯請求的台詞另附 `speaker_id`（那張卡的 id）；覆核的人物名稱後面加「〔初見：…〕」。
  - **標記**：`characters.may_be_json` 記這張卡可能是哪幾張卡（`repository.may_be`）。覆核（verify）多一種 `same_person`（`s:<卡>`）：這張卡與每張候選卡各附第一次出現前後的段落與幾句台詞所在的段落（每段一個代號），問模型是其中哪一張、`different`（另一個人），或 `unknown`。回答某張卡或 `different` 要在 `evidence` 引至少一段，沒引的不採用、也不算答過（下次再問）。答某張卡：用既有的合併（`merge_characters`）併進那張卡，台詞與記憶跟著過去；那張卡比這張晚出現時，它自己的名字以它原本出現的位置記連結，不會因為卡往前移而提早顯示（ADR-032）。答 `different`：清掉標記。答 `unknown`、或沒問到：標記留著（ADR-102 的 partial／續跑補問照舊涵蓋）。有標記的卡不再另問一般的 `identity`。
  - **名字後來揭曉**：照舊由 `same_as_ref` 合併（ADR-032），名字只從揭曉位置起顯示；名字只說她叫什麼，沒說她是不是那幾位之一，標記跟著留到有名字的卡上，由覆核再問。
  - **資料表（migration 37）**：`characters` 原本以（書、卡名）為唯一鍵，同一本書不能有兩張卡名相同的卡。要讓卡名維持原文的寫法，只能重建資料表：唯一鍵改為（書、卡名、`label`），一般的卡 `label` 是空字串，所以「同一個名字就是同一張卡」對一般的卡照舊。重建時暫時關掉外鍵（SQLite 不能在交易裡切換），結束前比對外鍵檢查沒有多出問題。找卡的地方只找一般的卡：`upsert_character`、名稱實體的卡、`character_for_form`、`reconcile_characters`、系列合併、名詞表的別名、覆核揭曉合併的卡、報告的名稱索引；重讀清卡時有標籤的卡不刪名詞表（那是其他卡的寫法）。
- 審閱後修正（同日，合併前）：
  - **另一個時期的人的卡**（前世的「母親」，ADR-101）原本把「母親（前世）」存成卡名：標籤當了名字，違反上面的原則（它會進名字比對的寫法、定名會替它提譯名）。改成卡名是原文的「母親」，模型讀到的時期存在新欄位 `characters.period`（NULL：故事當下的人；空字串：另一個人、沒說時期），`label` 是時期（沒說時期時是「另一人」），網頁顯示「母親（前世）」。給模型的照舊有時期，但當成模型的判讀、不是名字：人物卡（翻譯、讀場景、整理記憶）多 `other_person`、`period` 兩欄；以名字串稱呼人物的地方（`visible_names`、覆核、人物關係、角色印象、體例、定名、讀者檢查、場景的關係提示，`repository.model_name`）寫成「母親〔前世〕」，和事實的「〔前世〕」同一寫法。這種卡不是它的字找得到的卡：`alias_map` 不收、讀場景的「這個寫法屬於哪幾張卡」（`known_by`、`owners`）不算，所以不會讓現在的「母親」變得有歧義；它由 id 找到。重讀同一場、同樣的字與同樣的時期找回同一張卡（`repository.other_time_card`，以卡名＋`label` 找）。名字揭曉時照舊由 `same_as_ref` 合併，名字只從揭曉處起顯示。
  - **模型對人物的描述有自己的資料表** `character_notes`（卡、書、場景、位置、種類、內容）：ADR-101 時模型替原文沒名字的人取的稱呼（「人攫いの指示役の男」）原本記在場景紀錄 `state_json.model_labels`，跟著場景、不跟著卡，也沒有可見位置。改成記在卡上，位置是模型引的第一段，從那裡起看得到；重讀同一場時先刪這一場寫的再重寫；合併時跟著卡，清卡時一起刪。`model_labels` 與它在 `RECORD_ONLY` 的位置拿掉。它仍不是名字、別名、證據或名詞表，只用來分辨同名的卡（下一點）。
  - **同名的卡附上之前步驟記下的東西**：只有第一次出現的段落開頭（`first_seen`），通常看不出是誰的母親。同一份請求裡名字相同的卡（翻譯、讀場景、整理記憶、覆核的 `same_person` 與候選裡有同名人物的項目 `same_name_candidates`），除了 `first_seen`，再附 `earlier_model_reading`（模型之前寫的描述，與角色印象裡的角色定位；提示詞寫明是模型先前的判讀，不是原文）與 `relations_so_far`（到那個位置為止讀到、還沒被取代的關係，對方的名字用那個位置看得到的名字）（`visibility.tell_apart`）。一律以請求的位置為準：之後才寫的描述、之後才讀到的關係、之後才揭曉的名字都不給。常一起出場的人程式沒有現成的計數，不另算。沒有同名的卡時請求不變（ADR-094 記下的答案照樣沿用）。
  - **每個名字寫法有自己的首次位置** `character_forms`（卡、寫法、書、位置）：原本卡的其他寫法沒有自己的位置，跟著卡的 `known_from_ordinal`；重讀時後面才出現的卡以較早一場的寫法對到、卡往前移，只在後面出現的別名（「黒薔薇」）和卡名（「乙の母」）也跟著提早顯示（ADR-101 記下的待辦）。改成每個寫法記它第一次跟這張卡一起出現的位置（建卡、加別名、其他寫法、合併時帶過去取較早的），`character_view` 以它為準（也不早於名詞表記下的首次出現）；卡往前移時（`repository.seen_earlier`：重讀時以寫法對到後面才出現的卡；`upsert_character`、`merge_characters` 也一樣）只有對到的那個寫法從新位置起看得到，其他寫法留在原來的位置。沒有紀錄的寫法照舊跟著卡（舊書要重新匯入）。
  - migration 37 一起做（分支未合併，直接改 37）：`characters` 多 `period`；新表 `character_notes`、`character_forms`。搬書到別的系列、拆舊資料庫時兩張新表跟著卡。
  - 第二輪：
    - 網頁的「可能和…是同一人」每張候選卡附它開始被知道的位置，只列讀到的位置已經知道的卡（後面才出現的卡的名字不提早出現）。
    - 另一個時期的人揭曉名字後，有名字的卡留著那個時期（`period`，網頁顯示「リリア（前世）」）：不會變成現在的人、不被字找到；重讀時以時期＋寫法（卡名或別名）找回同一張卡（`other_time_card`）。
    - 合併後留下哪一張（覆核 `same_person`）：留有真名字的卡——沒有標籤的優先，都沒有標籤時名字是原文揭曉的優先，其他照舊留模型回答的那張；有標籤的卡吸收有名字的卡時，改用那個名字、拿掉標籤（`merge_characters`），名字仍只從它和這張卡一起出現的位置起看得到。
    - 同一次覆核的回答來自同一份快照：前面的回答已把卡併走時，後面的回答順著合併找到現在的卡（跨批次也一樣）；兩張已經是同一張、沒事可做的回答不算回答（不記為答過、列入沒問到，ADR-102 下次再問），也不算合併。
    - 同一次讀場景裡同一個寫法的兩個新人物是兩張卡：以「場景、寫法、這次讀的第幾個」為鍵（`characters.reading_key`），重讀同一場對回同一張。重讀時加上這次的別名與它們的位置；覆核答過「不是」的卡記在 `not_same_json`，重讀時這些卡不再標，只標沒問過的卡（新出現、也有這個寫法的卡）。
    - 名詞表的實體只綁一般的卡（有標籤的卡、另一個時期的卡不綁）；合併改寫其他卡的標記時一併更新 `updated_at`。
- 不做：標籤不當名字，所以不加在 `visible_names`、翻譯與審稿看到的說話者名字上（兩位「母親」在譯文裡本來就都是母親）；程式不比對誰像誰。
- 限制：舊書照舊要重讀才會套用（舊書是測試資料）。定名改卡名（rename）時，新名字沒有自己的首次位置，跟著卡。定名把有標籤的卡改名後標籤還在（只影響網頁顯示）。覆核的 `same_person` 只看每張卡第一次出現前後與最多 4 句台詞的段落，判斷所需的線索在別處時模型會答 `unknown`，標記留著。
